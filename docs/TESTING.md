# Проверка чтения и обновления PWA

## Автоматические проверки

```sh
npm ci
npm test
npm run build
node scripts/check-content.mjs
python3 -m unittest discover -s scripts -p 'test_*.py'
```

Сборка дополнительно проверяет, что все UI JS/CSS/шрифты/изображения попали в precache ровно один раз, код Workbox включён в сам worker, а тексты книг и API не кешируются как оболочка.

Веб-тесты проверяют данные IndexedDB, переход схемы v1 → v2, историю позиции прежнего издания, чтение проверенного текста из Cache Storage после повторного открытия базы, обрыв повторной загрузки, повреждение/удаление кеша, digest и структуру текста. Тесты жизненного цикла PWA проверяют однократную регистрацию и защиту открытой читалки от обновления, активированного в другой вкладке. Эти тесты не заменяют браузерную проверку service worker.

## Первая установка и запуск без сети

Использовать production-сборку: `npm run preview`. В dev-режиме worker отключён.

1. Открыть `/settings` на новом локальном порту или в чистом профиле браузера. Дождаться «Приложение сохранено на устройстве».
2. Открыть каталог, карточку тестовой книги, скачать и дождаться кнопки удаления загрузки. Прогресс 100% возможен только после проверки размера, SHA-256 и структуры.
3. Остановить preview-сервер, не открывая читалку заранее. Открыть её из карточки: это проверяет не только текст книги, но и ленивый chunk читалки.
4. Перейти во вторую главу, поставить закладку, перезагрузить страницу. Глава и закладка должны восстановиться при остановленном сервере.
5. Открыть новую вкладку с прямой ссылкой `/read/room-for-stories`. Она должна запуститься без сервера и восстановить данные.
6. Открыть `/downloads`, прочитать текст, удалить только загрузку. Позиция и закладки остаются. Попытка читать удалённый текст без сети показывает понятную ошибку.

Повторить на настоящих Android и iPhone, в установленной PWA и авиарежиме. Проверить закрытие браузера/приложения, перезапуск телефона, нехватку места и очистку браузером кеша. Localhost компьютера не доступен телефону как localhost — нужен HTTPS-стенд.

## Обновление приложения

1. Открыть читалку в первой вкладке и каталог во второй.
2. Собрать изменённую версию приложения, перезагрузить только вторую вкладку, дождаться предложения обновить.
3. Применить обновление во второй вкладке. Первая вкладка с читалкой не должна перезагружаться.
4. В первой вкладке сохранить и выйти, затем явно применить обновление. После перезагрузки восстановить главу/абзац и закладки.
5. Если издание книги обновлено, прежний locator должен остаться в IndexedDB `positionHistory`; новый текст открывается с первой главы. Закладки прежней версии не должны переносить пользователя по неверным ID нового текста.

Версия схемы IndexedDB, версия книги и версия service worker — независимые вещи. Для будущих несовместимых изменений нужна дополнительная проверка нескольких одновременно открытых версий приложения.

## Одна книга в двух вкладках

Использовать две вкладки одной версии приложения на одном origin. Для dev-сборки также проверить запуск с React StrictMode. Для аккаунта нужен доступный API и вход.

1. Открыть книгу в первой вкладке. Во второй открыть ту же книгу в том же режиме гостя/аккаунта. Должны появиться сообщение о другой вкладке и кнопка повтора; текст и сравнение мест аккаунта ещё не загружаются.
2. В первой вкладке перейти к другой главе, прокрутить текст и добавить закладку. Нажать повтор во второй, пока первая читает: открытие остаётся заблокированным.
3. В первой сохранить и выйти. Во второй повторить открытие: восстановятся последнее место и закладка. В аккаунте перед продолжением заново загружаются серверные данные и при необходимости показывается сравнение мест.
4. Повторить с закрытием первой вкладки вместо выхода. После повтора вторая должна открыться; при аварийном закрытии восстанавливается последнее фактически сохранённое место.
5. Открыть другую книгу: блокировка первой ей не мешает. Гость и разные аккаунты используют отдельные блокировки и базы.
6. Повторить в production/PWA после скачивания текста без сети для гостя. Аккаунт по-прежнему требует сети для проверки входа.

`reading-ownership.test.ts` проверяет взаимное исключение, удержание блокировки до окончания финальной записи, повтор после сохранения, раздельные книги/владельцев, отменённое открытие, повторный запуск эффекта, ошибку записи и недоступный Web Locks. При ошибке финальной записи блокировка остаётся до закрытия вкладки. Поддержка Web Locks обязательна для открытия читалки; используется HTTPS или localhost. Защита действует для вкладок с этим кодом на одном origin, не заменяет серверные конфликты и не управляет вкладками со старой версией приложения.

## Точный переход к закладке

1. Открыть тестовую книгу, увеличить шрифт до 32, прокрутить до середины длинного абзаца и поставить закладку кнопкой в шапке.
2. Прокрутить дальше в той же главе. Открыть «Закладки» и выбрать сохранённую запись. Под шапкой должна восстановиться та же часть абзаца, с учётом смещения внутри него.
3. Перезагрузить страницу: место должно сохраниться. Перейти в другую главу и снова открыть эту закладку: должны восстановиться глава, абзац и смещение.
4. Открыть оглавление и выбрать уже отображаемую главу. Должен открыться её первый абзац с нулевым смещением. Повторить переход к закладке.
5. Изменить размер/начертание/интервал и проверить переход повторно. Сохраняется доля абзаца, а не прежнее число пикселей. У конца главы браузер может ограничить прокрутку доступной высотой содержимого.

Переходы внутри текущей главы и между главами используют общий механизм восстановления после загрузки шрифтов. Проверка применима к гостевой читалке и читалке аккаунта; вход и серверные места проверяются отдельно.

## Незавершённое ручное сохранение места аккаунта

`position-choices.test.ts` проверяет сохранение точного payload/operation ID в IndexedDB v4, повтор после потери ответа и открытия базы заново, запрет повтора при конфликте ревизий, истёкшую сессию, смену аккаунта, конкурирующий выбор и отказ записи. Миграция из v3 сохраняет позиции и outbox; подтверждение ручного выбора не удаляет более поздние изменения чтения.

Для ручной проверки нужны работающие API/БД и вход по почте:

1. В профиле сравнить место устройства и аккаунта. Отключить сеть перед сохранением и нажать сохранение. Закрыть диалог и перезагрузить страницу.
2. Восстановить сеть и подтвердить вход тем же аккаунтом. В разделе мест чтения открыть незавершённое сохранение: выбранная глава/абзац и прежнее место аккаунта должны соответствовать исходному сравнению. Самостоятельной отправки при входе быть не должно.
3. Повторить сохранение. Если первый запрос уже был принят, повтор должен вернуть тот же результат без дополнительной серверной ревизии. Более позднее место чтения на устройстве и его outbox должны сохраниться.
4. Изменить серверное место со второго устройства до отправки исходного выбора. Получить конфликт; после перезагрузки повтор исходного выбора должен оставаться заблокированным. Отменить выбор, дождаться загрузки мест и сравнить заново.
5. Выйти при незавершённом сохранении: должно появиться предупреждение. Войти другим аккаунтом: сохранение первого аккаунта не отображается. После возвращения в исходный аккаунт оно снова доступно.

Это сценарий ручного сохранения места. Автоматический обмен outbox и офлайн-вход в аккаунт остаются отдельными задачами. Браузерный сценарий с живым API не подтверждается одними unit-тестами.

### Открытие читалки при незавершённом сохранении

`account-reading.test.ts` проверяет потерю ответа, повторное открытие IndexedDB, выбор из другой вкладки после загрузки мест и сохранённый конфликт. До подтверждения или отмены незавершённого выбора читалка не заменяет локальное место серверным. Отказ атомарный: история, закладки, outbox и сам выбор сохраняются. Локальное чтение доступно; выбор другой книги или другого аккаунта его не блокирует.

1. Создать незавершённое сохранение по сценарию выше. Открыть ту же книгу из полки аккаунта. Должно появиться объяснение и ссылка в профиль; выбора места аккаунта быть не должно, даже если локального места ещё нет или места совпадают.
2. Продолжить с места на устройстве (либо начать с начала, если места нет). Проверить, что незавершённое сохранение по-прежнему доступно в профиле, а более позднее чтение остаётся локальным.
3. Открыть сравнение в читалке, затем создать незавершённое сохранение этой книги в другой вкладке. Попытка выбрать место аккаунта в первой вкладке должна показать ошибку. После обновления мест отображается предупреждение; данные не удаляются.
4. В профиле подтвердить прежний выбор или явно отменить дальнейшие повторы, заново открыть книгу. Выбор серверного места снова доступен, если места различаются. Отмена не откатывает уже принятое сервером изменение.
5. Повторить с конфликтом ревизий; проверить, что книги без незавершённого сохранения и другой аккаунт открываются независимо.


## Чтение при сбое загрузки данных аккаунта

`account-reading.test.ts` проверяет восстановление локального чтения после повторного открытия базы, сохранение закладок и их удалений, outbox, времени и незавершённых выборов (включая конфликт). Проверка входа выполняется заново; гостевое хранилище, другой аккаунт, истёкшая сессия, недоступная сеть, отсутствующее место, прежнее издание и невалидный locator не позволяют открыть этот режим.

1. Войти в аккаунт, открыть тестовую книгу из его полки, перейти во вторую главу, поставить закладку и сохранить место.
2. Сделать недоступным только `/api/v1/positions/` или `/api/v1/bookmarks/` (например, ответ 503 в тестовом API), оставив `/api/v1/auth/session` доступным. Заново открыть читалку аккаунта.
3. На экране ошибки нажать «Продолжить с места на устройстве». Должна восстановиться вторая глава и местная закладка. Ошибочный ответ не считается пустым списком закладок и ничего не подтверждает в очереди. Дальнейшее чтение сохраняется на этом устройстве.
4. Повторить для книги без сохранённого места этого аккаунта: показать ошибку, не начинать с гостевого места или с начала. Сохранённое место прежнего издания также не подходит.
5. Между появлением экрана ошибки и нажатием кнопки завершить сессию или сменить аккаунт в другой вкладке. Открытие прежней базы должно быть отклонено. При полном отключении сети проверка входа также должна завершиться ошибкой.
6. Восстановить API и выбрать «Попробовать снова». Обычное сравнение серверного и локального места должно снова работать.

Это восстановление при частичной недоступности API. Полноценный офлайн-вход и автоматическая синхронизация требуют отдельной реализации.

## Статус сохранения аккаунта

`account-save-status.test.ts` проверяет отдельный подсчёт мест, изменений закладок (включая удаления), записей времени и других изменений, а также приоритет конфликтов/неподтверждённых сохранений и изоляцию аккаунтов от гостя. Пустая очередь не называется синхронизированной.

`position-choices.test.ts` дополнительно проверяет подтверждение конкретных operation IDs, повтор без расширения набора подтверждаемых записей, новое чтение во время запроса, отказ локальной транзакции после серверного успеха и совместимость с ранее сохранёнными выборами без списка operation IDs.

1. Войти в аккаунт с пустой локальной очередью, открыть профиль. Блок «Сохранение данных» должен показывать «Нет изменений, ожидающих отправки».
2. Открыть читалку аккаунта, поставить закладку, читать и сохранить/выйти. В профиле должны появиться «Сохранено на устройстве» и отдельные количества мест, изменений закладок и записей времени. Гостевые изменения в этот блок не входят.
3. Явно сохранить место аккаунта в разделе ниже. Подтверждённое изменение места исчезает из счётчика; закладки и время остаются. Если чтение продолжалось после начала сохранения, новое место остаётся в очереди.
4. Повторить с потерей ответа и перезагрузкой. Блок показывает неподтверждённое сохранение; повтор отправляет прежний вариант. При конфликте показывает необходимость сравнить места заново. Отмена повтора не очищает локальные изменения.
5. Выйти и войти другим аккаунтом. Статус и счётчики должны соответствовать только текущему аккаунту. При недоступном хранилище нельзя показывать пустую очередь как успешную проверку.

## Одновременное сохранение места в нескольких вкладках

`position-choices.test.ts` проверяет блокировку повторной отправки, отмены и замены выбора из второго подключения к IndexedDB, включая период между ответом API и коммитом локального подтверждения. После сетевой ошибки исходный выбор остаётся доступным для явного повтора или отмены. Другие книги и аккаунты независимы. Без Web Locks действия завершаются ошибкой до запроса и изменения сохранённых данных; требуется HTTPS/localhost и браузер с поддержкой Web Locks.

1. Войти в один аккаунт в двух вкладках одного origin. Создать неподтверждённое сохранение места и открыть его в обеих вкладках.
2. Задержать ответ `/api/v1/positions/choose` в тестовом API. Отправить выбор из первой вкладки. Во второй попытаться отправить его снова или отменить: должно появиться сообщение о сохранении в другой вкладке. Исходный выбор остаётся на устройстве; второго запроса нет.
3. Разрешить успешный ответ. Дождаться локального подтверждения: выбор исчезает в обеих вкладках, более позднее чтение остаётся в очереди.
4. Повторить с сетевой ошибкой: после завершения запроса выбор остаётся, отмена или повтор во второй вкладке доступны. Отмена не откатывает изменение, которое сервер мог уже принять.
5. Во время задержанного запроса проверить независимый выбор другой книги. Повторить для другого аккаунта в отдельном локальном хранилище.

Это координация вкладок одного origin с новой версией приложения. Межустройственные конфликты по-прежнему обрабатываются серверной ревизией; полная автоматическая синхронизация не реализована.

## Серверный протокол закладок

На отдельной тестовой PostgreSQL примените все `services/api/db/migrations/*.up.sql` по порядку, затем выполните:

```sh
cd services/api
TEST_DATABASE_URL='postgres://lumyboo:test@127.0.0.1:55433/lumyboo?sslmode=disable' go test -race ./...
```

База должна быть предназначена для тестов. `TestPostgresBookmarkChanges` создаёт временных пользователей и проверяет повторы операций, переиспользование UUID, параллельные изменения одной ревизии, конфликт со старым устройством, tombstones, явное восстановление, изоляцию аккаунтов, совместимость с импортом/прежними UUID закладок и откат неуспешной записи вместе с receipt. HTTP-тесты отдельно проверяют вход, Origin/CSRF, ожидаемого владельца, обязательные поля, валидацию текста и отсутствие кеширования приватных ответов. CI запускает интеграционные тесты и цикл миграций up/down/up. Список файлов определяется автоматически: применение идёт по возрастанию номеров, откат всех `*.down.sql` — в обратном порядке. Для новой миграции нужны оба файла.

## Устойчивые клиентские запросы изменения закладок

`bookmark-choices.test.ts` проверяет модуль явных изменений закладок: IndexedDB v5, сохранение запроса до отправки, неизменный UUID/payload/revision при повторе после потери ответа и переоткрытия базы, сохранение конфликтов, изоляцию аккаунтов, ожидаемого account ID/CSRF на клиентском запросе и отклонение неверных подтверждений. Два подключения к одной базе проверяют Web Locks до коммита локального подтверждения. Удаление и повторное создание во время запроса не очищают более позднюю outbox; сбой локального подтверждения откатывает очистку целиком. Миграция v4 → v5 сохраняет прежние данные и выборы позиций.

Профиль использует этот модуль для явного сохранения отдельных закладок. Автоматический обмен пока не подключён. `rememberBookmarkChoice` принимает явно выбранный locator и ожидаемую серверную ревизию из `/bookmarks/state`, включая tombstones. Для удаления одного старого ключа из outbox недостаточно: требуется полный проверенный locator. `sendBookmarkChoice` отправляет только сохранённый запрос и подтверждает только зафиксированные до него операции. Полученный receipt не применяется как свежий снимок сервера и не заменяет локальные закладки. После конфликта нужен новый просмотр состояния; отмена не откатывает уже принятый сервером запрос и не очищает outbox.

Запуск: `npm test` и `npm run build` из корня. Серверный протокол отдельно проверяется Go/PostgreSQL-тестами выше. Живая межустройственная и браузерная приёмка клиентского модуля остаётся для подключения интерфейса.


## Явное сохранение закладок из профиля

## Серверные накопительные отчёты времени чтения

На отдельной тестовой PostgreSQL применить все миграции по порядку, включая `006_reading_sessions.up.sql`, затем выполнить:

```sh
cd services/api
TEST_DATABASE_URL='postgres://lumyboo:test@127.0.0.1:55434/lumyboo?sslmode=disable' go test -race ./...
```

База должна быть предназначена только для тестов. Интеграционный тест `TestPostgresReadingSessions` создаёт временных пользователей и роль с ограниченной записью для проверки атомарного отката при отказе вставки receipt. Для него требуется право создавать тестовые роли (в CI используется отдельная PostgreSQL).

Протокол: `POST /api/v1/reading-sessions/apply` принимает `accountId`, `operationId` и `session` (`sessionId`, `deviceId`, `bookId`, `version`, `day`, `milliseconds`). Требуются cookie входа, Origin приложения и `X-CSRF-Token`. `milliseconds` — накопленный целочисленный итог одной сессии от 1 до 86 400 000, а не добавка. Верхняя граница — технический предел одной записи, не проверка суммарного времени дня или достоверности чтения.

Тесты проверяют:

- Точный повтор UUID/payload возвращает исходное подтверждение, в том числе после более нового отчёта; новый UUID со старым/равным итогом не уменьшает время, не складывает снимки и не повышает ревизию.
- Параллельные снимки сходятся к наибольшему накопленному итогу; два одновременных повтора дают одну запись/receipt. Разные сессии/устройства не объединяются по книге и дню.
- У сессии неизменны устройство, книга, издание и заявленный день. Смена этих полей возвращает конфликт. Неверные календарные даты, нулевые/отрицательные/дробные/слишком большие итоги и неизвестные поля отклоняются.
- Владельцы изолированы, один session/operation UUID может независимо существовать у разных владельцев. UUID операции делит пространство с закладками и позициями: смена вида операции возвращает конфликт. Чужая/отсутствующая запись на GET даёт 404.
- Ошибка FK или записи receipt откатывает изменение целиком; повтор после устранения ошибки безопасен. Удалённый аккаунт не может отправлять отчёты.
- HTTP-проверки входа, Origin/cross-site, CSRF, ожидаемого аккаунта, текущего издания, no-store и безопасных ошибок выполняются до доступа к хранилищу.

`GET /api/v1/reading-sessions/{sessionId}` получает актуальный снимок только своего аккаунта. Receipt из POST может быть старее него: его нельзя применять как новый серверный снимок или подтверждение более поздних локальных изменений.

День здесь заявлен клиентом без подтверждённого часового пояса. Эти отчёты не начисляют XP, дневной план, серию, завершение книги или результат гонки. Веб-таймер фиксирует устройство и версию книги для новых сессий; явная отправка из профиля описана ниже. Старые локальные сессии без этих метаданных остаются на устройстве.

## История сохранённого времени с устройств

Применить все миграции, включая `007_reading_session_history.up.sql`, к отдельной тестовой БД. `TEST_DATABASE_URL=… go test -race ./internal/readingsessions ./internal/httpapi` проверяет приватность, ошибки и границы страниц; `npm test` — проверку владельца ответа, отмену запросов и формат длительности.

`GET /api/v1/reading-sessions/?limit=20` возвращает `accountId`, `items`, `nextCursor`. Пустой `nextCursor` завершает список; следующий запрос передаёт полученный cursor. Это живые страницы: новые записи перед курсором появляются при обновлении с начала, а накопительные обновления не сдвигают записи. ## Автоматическое сохранение времени

`npm run test -w apps/web -- src/lib/reading-time-auto.test.ts src/lib/reading-session-sync.test.ts` проверяет открытие аккаунта/очередь, проверку живой сессии перед каждым пакетом, офлайн → online, задержки повторов и Retry-After, отсутствие параллельных пакетов, другую вкладку, остановку при ошибках входа/конфликта/хранилища, отмену при размонтировании и неизменный повтор отправленного снимка.

### Сетевые задержки и отмена запросов

`npm run test -w apps/web -- src/lib/api.test.ts` проверяет обработчик HTTP совместно с автоматическим отправителем на управляемых часах. `Retry-After` поддерживает целые секунды и HTTP-даты (включая старые форматы); прошедшая/неверная дата не задаёт дополнительную задержку. Дроби, отрицательные числа и экспоненциальная запись не считаются числом секунд. Для будущей даты задержка округляется вверх до секунды: при `12:00:00.250` и дате `12:01:00 GMT` повтор происходит через 60 секунд, online-событие не ускоряет его.

Таймаут 12 секунд действует и на чтение тела ответа. Отмена или таймаут при чтении тела ошибки сохраняют исходную причину отмены, вместо превращения в окончательную ошибку API/входа. Таймер освобождается после завершения/отмены. Неразбираемое тело без отмены по-прежнему даёт безопасное общее сообщение API. Это автоматические проверки с фиктивным fetch; проверка реальной сети и физических устройств проводится отдельно.

## Получение фрагментов при открытии книги

`npm run test -w apps/web -- src/lib/reading-coverage-receive-auto.test.ts` проверяет настоящий загрузчик с fake-indexeddb и Web Locks: одно получение за открытие, пустую историю, ровно 50 изменённых абзацев, объединение поздних местных наблюдений без очистки очереди, offline/online, задержку после 503 без обхода через online, занятый lock, смену владельца, неверное издание и поздний ответ после отмены. Успешное получение завершает планировщик без фонового опроса. Тесты загрузчика отдельно покрывают пагинацию и транзакционный откат.

1. Сохранить фрагменты книги в тестовом аккаунте на A. На B открыть книгу из полки аккаунта: GET `/reading-coverage/{bookId}?version=…` выполняется после открытия текста, без кнопки в профиле. Полученные фрагменты дополняют coverage только этого аккаунта и издания; позиция, закладки и время не меняются.
2. Читать на B во время задержанной загрузки: новые местные наблюдения и их очередь сохраняются. Повторный GET после успешного получения не выполняется до следующего открытия книги; пустой список также завершает получение.
3. Вернуть 503 или удерживать coverage-lock: повтор выполняется с задержкой. Закрыть читалку до ответа: локального импорта и следующих запросов нет. Повторное открытие запускает новое получение с первой страницы.
4. При 401, смене аккаунта или неверном ответе показать сообщение, остановить повторы и оставить чтение на устройстве доступным. Повторить получение можно из профиля. Гостевая читалка не запрашивает покрытие аккаунта.

Браузерная проверка с живым API и проверка на двух физических устройствах остаются отдельной приёмкой; автоматические тесты используют фиктивный HTTP и настоящую клиентскую логику загрузки/хранения.


## Возвращение во вкладку читалки

После успешного получения фрагментов возвращение в видимую читалку с фокусом запускает новое однократное получение. События focus/visibilitychange во время загрузки не запускают параллельные запросы; они также не обходят backoff или остановку при ошибке входа/проверки данных. Периодического опроса после успеха нет.

`reading-coverage-receive-auto.test.ts` дополнительно проверяет повтор после успеха/пустой истории, добавление новых серверных диапазонов без изменения местной очереди, offline → online, сохранение backoff/остановки и отсутствие запросов после cleanup.

1. Открыть книгу аккаунта на устройстве B и дождаться получения. Переключиться на другую вкладку; на A сохранить новые фрагменты той же книги.
2. Вернуться в B: новые фрагменты дополняют местные. Позиция, закладки, время и неподтверждённые местные операции сохраняются. Оставить вкладку активной: периодического GET нет.
3. Задержать GET и несколько раз переключить фокус: параллельных загрузок нет. Вернуть 503: переключение вкладок не сокращает задержку повтора. После неверного издания или отказа входа автоматические попытки остаются остановлены до повторного открытия читалки; получение можно повторить в профиле.
4. Вернуться без сети и затем восстановить сеть: получение возобновляется. Закрыть читалку до ответа: поздние данные не записываются; события фокуса больше не вызывают запросов.

Реальные браузеры и два физических устройства требуют отдельной проверки.

## Получение фрагментов после восстановления сети

`npm run test -w apps/web -- src/lib/reading-coverage-receive-auto.test.ts` дополнительно проверяет reconnect после успешной и пустой истории, первоначальный offline, сохранение поздней локальной очереди, Retry-After, смену аккаунта, активный запрос и отмену. Используются настоящий загрузчик, fake-indexeddb и фиктивный HTTP.

В открытой читалке аккаунта дождаться успешного GET фрагментов, отключить сеть, сохранить новые фрагменты той же книги на другом устройстве и вернуть сеть на первом. Без смены вкладки должен пройти новый GET; диапазоны объединяются, местные операции сохраняют UUID/payload. Повторить с первоначально пустой историей. При 503 с Retry-After события online не сокращают задержку; после смены аккаунта или закрытия читалки они не запускают старый загрузчик. Эта проверка на реальных устройствах пока не выполнена.


## Возврат к непоказанному абзацу

В оглавлении «Открыть абзац N» ведёт к началу первого абзаца главы, который ещё не показан целиком. Частичные диапазоны с любым пробелом также оставляют абзац доступным для возврата. Когда все абзацы главы показаны целиком, кнопки нет; название главы по-прежнему открывает её начало. При загрузке/ошибке coverage переход к абзацу не предлагается, переход по названию доступен.

`npm run test -w apps/web -- src/lib/reading-coverage-summary.test.ts` проверяет порядок абзацев, объединение диапазонов и микропробелы, полностью показанную/пустую главу, изоляцию изданий и обновления через IndexedDB.

В браузере открыть книгу, затем оглавление и кнопку абзаца другой главы; повторить переход в текущей главе и перезагрузить страницу. Проверить восстановление выбранного места. Главы, которые не открывались, остаются непоказанными. Проверить отдельно гостя и аккаунт, Blanc/Noir и узкий экран. Переход не отмечает книгу прочитанной.


## Возврат внутрь частично показанного абзаца

Кнопка «К непоказанному участку · абзац N» в оглавлении открывает первый пробел в сохранённых диапазонах первого неполностью показанного абзаца главы. При непоказанном начале используется offset 0; после непрерывного показанного начала — его конец. Перекрывающиеся диапазоны объединяются, микропробелы не округляются. Полная глава не предлагает переход. Геометрическая позиция приблизительная, особенно после изменения шрифта; переход не подтверждает прочтение.

Тест `reading-coverage-summary.test.ts` дополнительно проверяет непоказанные начало/середину/конец, микропробел, неупорядоченные перекрытия и выбор следующего абзаца после объединения записей.

В браузере с тестовым IndexedDB подготовить длинный абзац с ranges `[[0, 0.4], [0.8, 1]]` текущего издания. Открыть оглавление и перейти к непоказанному участку: в сохранённом locator должен быть offset 0.4, текст открывается внутри абзаца. Повторить переход в текущей главе, перезагрузить страницу и проверить восстановление. Для `[[0.2, 1]]` переход ведёт к началу, для `[[0, 1]]` выбирается следующий неполный абзац. Проверить Blanc/Noir и компактную рамку.

## Первый непоказанный участок книги

Общая кнопка над главами выбирает первый непоказанный участок по порядку всей книги, независимо от текущей главы. После заполнения пропуска она ведёт к следующему. Пустые главы пропускаются; если все абзацы показаны целиком, кнопка исчезает. При загрузке или ошибке фрагментов она недоступна. Это навигация по показанным участкам, без подтверждения прочтения.

В браузере открыть первую главу, перейти сразу в последнюю, затем в оглавлении нажать «Первый непоказанный участок книги». Проверить возврат к пропуску первой главы. После его показа повторить: переход должен вести в первую пропущенную главу. Проверить сохранение позиции после перезагрузки, отдельно гостя/аккаунт, Blanc/Noir и узкий экран. `reading-coverage-summary.test.ts` проверяет порядок глав, микропробелы, продвижение после объединения фрагментов, полностью показанную книгу и пустые главы.

Восстановление и захват locator используют одну видимую границу: фактический низ sticky header плюс 12px. При проверке перехода точка `paragraph.top + paragraph.height * offset` должна располагаться у этой границы (допуск 1px на округление scrollTop), включая текущую главу и reload. Проверить отдельно закладку и изменение шрифта.

## Выбор любого непоказанного участка главы

В оглавлении раскрыть «Выбрать непоказанный участок» у пропущенной главы. Список содержит каждый пробел в порядке текста, с номером и началом абзаца. Выбрать третий абзац: открывается нужная глава, а предыдущие пропущенные абзацы остаются в списке при повторном открытии. Показанный целиком участок исчезает. Проверить переход и в текущей главе, восстановление после reload, гостя и аккаунт, Blanc/Noir.

Для абзаца с диапазонами `[[0.1, 0.4], [0.400001, 0.8]]` доступны три отдельные цели с offset 0, 0.4 и 0.8. В главе с более чем 20 пробелами изначально показываются 20; «Показать ещё» открывает следующие 20, сворачивание и раскрытие возвращает первые 20. Загрузка/ошибка покрытия не показывает фиктивный список. Выбор и раскрытие списка сами по себе не пишут в coverage/outbox. `reading-coverage-summary.test.ts` проверяет дополнение диапазонов, микропробелы, порядок, объединение наблюдений, исключение других изданий/книг/глав, пустые главы и обновление целей после заполнения пропусков.

### Время за текущей книгой

Открой книгу, оставь видимый текст с фокусом на несколько секунд и нажми «Время чтения». Проверь время за сегодня и за всё время; при открытом окне значения не должны расти. Закрой окно, почитай и открой повторно: время увеличивается. Перезагрузка сохраняет результат. Другая книга/издание, гость и аккаунты не складываются. При ошибке IndexedDB окно показывает ошибку с повтором вместо нулей. Сегодня определяется датой устройства и обновляется после смены дня. Это локальные сохранённые секунды, без прибавления серверной истории.

Автотесты `book-reading-time.test.ts` проверяют накопительные снимки, разные дни/издания/книги, старые сессии без издания, пустые данные, изоляцию владельцев после переоткрытия и неизменность outbox.

В «По дням» проверь сумму сессий одного дня и порядок дат от новых к старым, в том числе переход месяца/года. Дни с нулевыми снимками не выводятся; при пустой истории показано отдельное сообщение. Для истории из 26 дней сначала доступны 20, кнопка раскрывает ещё 6 и исчезает. Закрытие и повторное открытие сбрасывает список к первым 20. Обновлённый накопительный снимок заменяет прежний вклад дня. Дата выводится как ДД.ММ.ГГГГ без преобразования часового пояса. Тесты также проверяют точность суммы множества коротких сессий, сортировку через границу года и неизменность очереди.

## История гостевого времени в профиле

`npm run test -w apps/web -- src/lib/local-reading-time.test.ts src/lib/book-reading-time.test.ts` проверяет суммы в целых миллисекундах, накопительные snapshots, объединение книг/изданий/legacy-сессий только в общей истории, изоляцию владельцев, reopen, пропуск нулевых дней, смену даты и неизменность очереди/metadata. Отказ хранилища должен отклонять запрос, после восстановления повтор снова возвращает сохранённые данные.

1. На чистом тестовом origin открыть профиль и раскрыть «История чтения по дням»: показать пустое состояние.
2. Почитать две книги гостем. В профиле дни объединяют их сохранённые секунды, общий счётчик показывает целые минуты. Время аккаунта не прибавляется.
3. В отдельной тестовой базе подготовить 25 дней с положительным временем. Проверить порядок от новых к старым, первые 20 → «Показать ещё» → 25. Свернуть/раскрыть — снова 20; перезагрузка сохраняет данные.
4. При открытом профиле сменить дату устройства: «минут сегодня» обновляется. При отказе чтения IndexedDB показывается ошибка с повтором, а не нули. После восстановления нажать «Повторить».
5. Проверить оформление Blanc/Noir и прокрутку списка внутри компактной рамки.

## История времени аккаунта на устройстве

1. Войти в тестовый аккаунт A и открыть профиль → «Время чтения аккаунта» → «На этом устройстве». Пустое локальное время даёт нули и отдельное сообщение при раскрытии истории, даже если серверная история содержит записи.
2. Почитать книги из полки аккаунта A. Локальные сохранённые сессии (включая ещё не отправленные) обновляют сегодняшнее и общее время. Разные книги/издания одного дня суммируются, накопительный снимок заменяет прежнее значение. Получение серверной истории не увеличивает эти суммы.
3. Для 25 дней проверить 20 → 25 → свернуть/раскрыть → 20. Даты идут от новых к старым, дни без времени пропускаются. Гостевая история на том же экране раскрывается независимо.
4. Выйти и войти в аккаунт B: суммы, раскрытие и ошибки A не переносятся. Вернуться в A: его данные сохраняются. Гостевые суммы не меняются. Проверить reload, смену даты устройства, отказ IndexedDB и «Повторить» после восстановления.
5. Проверить Blanc/Noir и компактную рамку. `local-reading-time.test.ts` проверяет liveQuery обновление аккаунта, изоляцию другого аккаунта, legacy/разные издания, reopen и неизменность ожидающих операций.

## Обмен между двумя HTTPS-сессиями с PostgreSQL

Сквозной серверный тест создаёт отдельную случайную схему, применяет в ней все
`services/api/db/migrations/*.up.sql` и удаляет её после проверки. Существующие
таблицы и данные не изменяются. Роль тестовой БД должна иметь право `CREATE SCHEMA`.
При отсутствии `TEST_DATABASE_URL` тест пропускается; CI запускает его в задании
`migrations` с настоящим PostgreSQL.

```sh
TEST_DATABASE_URL='postgres://lumyboo:local-development-only@127.0.0.1:5432/lumyboo?sslmode=disable' \
  go -C services/api test -race -count=1 \
  -run 'TestPostgres(ReadingJourneyTwoSessions|AccountSwitchWithLostVerifyReply|ReadinessRequiresAccountSchema)' -v ./internal/httpapi
```

`TestPostgresReadingJourneyTwoSessions` использует HTTPS-сервер, Secure/HttpOnly
cookies и независимые cookie jars двух устройств, другого пользователя и гостя.
Вход проходит через реальные API выдачи/проверки кода и PostgreSQL. Доставка письма
заменена тестовым почтовым ящиком в памяти; сгенерированный код проверяется обычным
сервисом. Перед вторым входом только в тестовой схеме сдвигается время ограничения
повторной отправки; до этого тест проверяет отказ 429.

Проверяются перенос полки и закладок с повторами, получение места во второй сессии,
продолжение и конфликт устаревшего места, повтор прежнего запроса после нового
чтения, удаление закладки без восстановления повторным импортом, накопительное
время двух устройств без удвоения, объединение перекрывающихся фрагментов,
изоляция другого аккаунта, выход из одной сессии и истечение другой. Повтор после
потери ответа моделируется повторной отправкой точного запроса после его
подтверждённого выполнения; настоящий обрыв TCP этим не проверяется.

`TestPostgresReadinessRequiresAccountSchema` проверяет `/readyz` на полной схеме,
после удаления необходимой колонки и после удаления таблицы. Неполная схема
возвращает 503; `/healthz` продолжает возвращать 200. Readiness проверяет наличие
таблиц/колонок и права чтения, необходимые API аккаунтов; не применяет миграции и
не заменяет контроль ограничений/индексов или проверку SMTP.

Эти тесты проверяют серверный путь, но не работу интерфейса, IndexedDB, PWA,
автоматическую отправку позиций/закладок или два физических устройства. Для
приёмки C по-прежнему нужен полный пользовательский путь в двух браузерах и на
целевых телефонах с доступным HTTPS-окружением.

## Браузерный путь с настоящим API и отдельными хранилищами

### Челлендж двух аккаунтов: HTTP и PostgreSQL

```sh
cd services/api
TEST_DATABASE_URL='postgres://lumyboo:local-development-only@127.0.0.1:5432/lumyboo?sslmode=disable' \
  go test -race ./internal/httpapi -run '^TestPostgresChallengeJourneyTwoAccounts$' -count=1 -v
```

Тест создаёт изолированную схему со всеми миграциями и удаляет её после проверки.
Три клиента имеют отдельные cookie-хранилища; настоящие HTTPS-запросы проходят
OTP-вход, CSRF/проверку владельца и PostgreSQL. Перехвачена только доставка OTP,
а часы хранилища челленджей управляются внутри теста; системное время и
production-конфигурация не меняются. Время чтения отправляется через API как
заранее заданные отчёты, а не накапливается браузерным таймером.

Оба формата проходят создание → код → предварительные условия без состава
команды → вступление → чтение разных книг → общий прогресс → выход → итог
семидневного периода. Проверяются повтор создания/вступления/отчёта/выхода,
порог с точностью до миллисекунды, поздняя запись до и после конца периода,
ничья и смена мест, фиксированный результат вышедшего, разные личные цели без
рейтинга, отсутствие чужих ID/почты/книг в полном HTTP-ответе и изоляция третьего
аккаунта. Отдельные тесты `TestPostgresChallengeProgress` проверяют DST,
несколько устройств и миграцию снимка выхода.

Для браузерной проверки использовать стенд ниже с **разными** тестовыми email.
Создать команду на первом адресе, вступить по коду на втором; до вступления
состав команды не должен отображаться. Читать разные книги именно в читалках
аккаунтов (из полки аккаунта в профиле), сохранить и выйти. В разделе «Вместе»
обновить данные и раскрыть «Твои дни и время»: каждый видит собственные минуты,
а у другого участника — только цель, выполненные дни, место и отметку выхода.
После выхода одного участника второй остаётся, а вышедший сохраняется в списке.
Для проверки активного дня без ожидания старта допустимо изменить `start_day`
только созданного тестового челленджа в одноразовой `journey_*` БД стенда;
зафиксировать такое ускорение отдельно от настоящего календарного прогона.

Порог выполнения, позднюю отправку после конца периода и смену мест проверяет
HTTP-тест выше. Браузерная приёмка этих переходов требует отдельного прогона с
чтением до цели, задержкой отправки и сменой календарных дней. Проверка HTTP и
локального браузера не заменяет HTTPS staging и физические Android/iPhone.

### Запуск браузерного стенда

Предусловия: Node/npm и Go из README, Docker Compose с PostgreSQL и Mailpit
(`docker compose -f ops/compose.yaml up -d postgres mailpit`). Запуск:

```sh
python3 scripts/reading_journey.py
# Другой контейнер PostgreSQL:
# python3 scripts/reading_journey.py --postgres-container my-postgres
```

Скрипт собирает web/API, создаёт случайную временную БД и применяет все миграции.
Использует локальные development-реквизиты из compose, PostgreSQL на 5432 и SMTP
на 1025. Открывает два loopback-адреса: `http://127.0.0.1:4311` и
`http://localhost:4312`, с разными cookies/IndexedDB и двумя API на 8311/8312,
проверяющими соответствующий Origin. API, PostgreSQL и доставка OTP настоящие;
замены ответов нет. Порты должны быть свободны. Ctrl+C/SIGTERM останавливает
API и удаляет только созданную БД; рабочая `lumyboo` не меняется. После SIGKILL
автоматическая очистка невозможна. Браузерные данные и тестовые письма остаются;
для независимого прогона использовать чистые профили и новый `@example.test`
адрес. Скрипт предназначен только для локальной проверки, не для размещения.

1. На первом адресе открыть «Комната для историй», перейти ко второй главе,
   поставить закладку, сохранить и выйти. В карточке добавить книгу на полку.
2. Войти с уникальным `@example.test` email. Взять код из Mailpit на
   `http://127.0.0.1:8025`. Явно скопировать гостевые книги и закладку; сравнить
   и сохранить гостевое место в аккаунте. Подтверждения должны показывать
   правильный аккаунт и главу. Гостевые данные остаются на устройстве.
3. На втором адресе до входа аккаунта быть не должно. Войти тем же email новым
   кодом (ограничение повторной отправки — минута). Убедиться, что полка,
   закладка и серверная глава совпадают с перенесёнными.
4. Открыть книгу из полки аккаунта. Она должна открыть вторую главу с закладкой
   и остаться доступной после подготовки. Сообщение «уже открыта в другой
   вкладке» при отсутствии второго читателя — ошибка. Повторить после выхода
   из читалки и reload: цикл проверки входа не должен вытеснять читателя.
5. Удалить местную закладку, перейти к третьей главе, сохранить и выйти.
   Место и новое удаление закладки отправляются при выходе без ручных действий
   в профиле. На первом адресе обновить профиль и открыть аккаунтную
   книгу: третья глава, закладок нет; гостевая закладка по-прежнему отдельная.
6. Для проверки времени держать читалку видимой и в фокусе; скрытый клиент
   время не накапливает. Проверки потери ответа, конфликтов, выхода/смены
   владельца и поздней записи выполнять по разделам выше.

При пересборке приложения с уже установленным service worker сначала выйти из
читалки и применить «Обновить приложение»; простой reload может оставить старую
оболочку. Этот локальный путь не заменяет HTTPS staging, физических Android/iPhone
и полной приёмки времени, покрытия, обрывов сети и автоматического обмена.

### Потеря ответа после сохранения времени и фрагментов

```sh
python3 scripts/reading_journey.py --drop-first-reading-response
python3 -m unittest discover -s scripts -p 'test_reading_journey.py' -v
```

Флаг включает обрыв первого успешного ответа `POST /reading-sessions/apply`
и `POST /reading-coverage/apply` отдельно на каждом из двух адресов. Прокси
сначала передаёт настоящий запрос API и полностью получает успешный ответ,
затем закрывает клиентское соединение без HTTP-ответа. Серверная запись уже
выполнена. Следующий запрос проходит обычно; ошибки API, вход и остальные
маршруты не затрагиваются. Без флага обрывы выключены. В консоли появляется
`Lost successful reading response` с портом и маршрутом, без тела запроса.

1. Войти на первом адресе, открыть книгу аккаунта, держать текст видимым
   и в фокусе, затем сменить главу. Дождаться двух сообщений об обрыве в консоли
   стенда. Запись времени должна остаться доступной для повтора; показанные
   фрагменты не должны исчезнуть. При быстром автоматическом повторе ошибочный
   статус может уже смениться обычным.
2. Сохранить и выйти, дождаться автоматического повтора. Очередь времени и
   фрагментов должна очиститься, место чтения остаётся отдельной операцией.
   Обновить страницу: подтверждённые записи не возвращаются в очередь.
3. Войти тем же аккаунтом на втором адресе. В «Сохранённое время с устройств»
   сравнить длительности с первым клиентом. Открыть книгу аккаунта и оглавление:
   фрагменты первого клиента должны дополнить местные, включая главу, которую
   второй клиент ещё не показывал. Само получение не создаёт новое время.
4. Почитать на втором адресе, повторить потерю ответа и восстановление очереди.
   На первом обновить серверную историю: записи двух устройств различаются,
   повтор не создаёт вторую запись одной сессии и не удваивает её длительность.

Тест прокси проверяет реальное закрытие HTTP-соединения после ответа upstream,
точную передачу повторного тела, одноразовость при конкурентных запросах,
изоляцию двух адресов и исключение ошибочных/нечитательских запросов. Upstream
в этом тесте технический; браузерный прогон требует настоящих API/PostgreSQL.
Режим проверяет потерю ответа, но не заменяет отключение сети на телефоне,
HTTPS, истечение сессии или приёмку C целиком.

### Сохранение места при выходе из читалки аккаунта

1. На стенде выше войти на A, открыть книгу аккаунта, перейти во вторую
   главу и нажать «Сохранить и выйти». В профиле место устройства и аккаунта
   совпадает; отдельное сравнение/сохранение не нужно. На B войти тем же
   аккаунтом и открыть книгу: восстановится вторая глава.
2. Открыть книгу одновременно на A и B. На B перейти в третью главу и выйти
   кнопкой закрытия читалки. На A перейти в четвёртую и сохранить: появится
   конфликт. Выйти с местом на устройстве. В профиле A должны остаться местная
   глава 4, серверная глава 3 и незавершённое сохранение с конфликтом.
3. При потере ответа повторить сохранение в окне выхода: повтор использует
   прежние operation ID, locator и expectedRevision. После reload выбор
   доступен в профиле. Если вход истёк или аккаунт сменился, прежнее место
   не отправляется новому владельцу. Отдельно проверить отказ IndexedDB:
   при ошибке местного сохранения выход с несохранённым местом не предлагается.
4. После ошибки загрузки серверного снимка продолжить с локального места:
   выход сохраняет данные на устройстве и предлагает сравнение в профиле,
   не использует выдуманную нулевую ревизию.

`reader-position-save.test.ts` проверяет известную/нулевую ревизию, потерю
ответа и точный повтор после reopen, конфликт, прежний незавершённый выбор,
истечение входа, другого владельца, гостя и отказ записи. Флаг
`--drop-first-reading-response` затрагивает только время/фрагменты; для места
и закладок есть отдельный `--drop-first-save-response`, описанный ниже.
Сохранение при выходе относится к кнопкам приложения; закрытие вкладки,
фоновая отправка мест и закладок ещё не покрыта; сохранение закладок при выходе описано ниже.


### Закладки при выходе из читалки аккаунта

1. На двух адресах стенда выше войти в один тестовый аккаунт. На A открыть
   книгу, поставить закладку и нажать «Сохранить и выйти». В профиле закладка
   появляется в аккаунте без отдельного ручного сохранения. На B открыть книгу:
   закладка загружается вместе с местом.
2. На B удалить полученную закладку и выйти кнопкой закрытия читалки. На A
   снова открыть книгу: закладка отсутствует. Добавление и удаление в течение
   одного чтения при исходно отсутствующей закладке не создаёт серверную запись.
3. Для конфликта открыть книгу на обоих адресах с одной закладкой. На B удалить
   её и выйти; на A удалить её и выйти. Изменение A сохраняет конфликт в профиле,
   не перезаписывая новую ревизию. Ошибка предлагает повтор или выход с данными
   на устройстве. Место могло уже сохраниться до ошибки закладки.
4. При потере ответа POST `/bookmarks/apply` повтор в окне выхода использует тот
   же UUID, locator, deleted и expectedRevision. После перезапуска сохранённый
   запрос доступен в профиле; уже подтверждённые закладки пакета не отправляются
   повторно при повторе в окне. Истечение входа и другой аккаунт блокируют отправку.
5. Прежние изменения этой книги, оставшиеся до открытия читалки, требуют
   сравнения в профиле. Автовыход не использует свежую ревизию для молчаливого
   перезаписывания старой правкой. При ошибке начальной загрузки закладок
   автоматического сохранения нет. Гостевые данные не отправляются.

`reader-bookmark-save.test.ts` проверяет ревизии создания/удаления/восстановления,
сохранение точного запроса и повтор после reopen, частичное успешное сохранение,
конфликт, прежние изменения и запросы, истечение входа, другого владельца и отказ
записи. `bookmark-choices.test.ts` дополнительно проверяет отказ местного
подтверждения и сохранность более поздних правок. Фоновая отправка при закрытии
вкладки и приёмка на физических устройствах сюда не входят.

### Потеря ответа при выходе: место и закладки

```sh
python3 scripts/reading_journey.py --drop-first-save-response
# Независимые обрывы всех четырёх маршрутов:
# python3 scripts/reading_journey.py --drop-first-save-response --drop-first-reading-response
```

Этот режим обрывает первый успешный ответ `POST /positions/choose` и
`POST /bookmarks/apply` отдельно на каждом адресе, после полного ответа
настоящего API. Запись уже выполнена; повтор идёт на тот же API. По умолчанию
режим выключен. Ошибки, включая 401 и 409, не расходуют обрыв; вход, импорт
гостевых закладок и GET не затрагиваются. Сохранение гостевого места через
профиль также использует `/positions/choose` и может первым израсходовать
обрыв: для проверки именно выхода начать с новой книги аккаунта без такого
переноса либо перезапустить стенд с новой БД.

1. Войти на A, добавить книгу в полку аккаунта и открыть её. Перейти во вторую
   главу, добавить закладку, нажать «Сохранить и выйти». В консоли должен быть
   обрыв `/positions/choose`; в окне выхода — ошибка и возможность повтора.
2. Нажать повтор: подтверждается прежнее место, затем обрывается ответ
   `/bookmarks/apply`. Повторить ещё раз. Выход должен завершиться, а профиль
   не должен показывать неподтверждённые запросы места или закладок. Обновить
   страницу: запросы не возвращаются. Сверить серверные ревизии: повтор
   не увеличивает ревизию сверх одной успешно применённой операции.
3. Войти тем же аккаунтом на B, открыть книгу: вторая глава и одна закладка.
   Удалить закладку, перейти в третью главу, выйти. Повторить после каждого
   из двух обрывов. На A снова открыть книгу: третья глава, закладок нет.
4. Отдельно повторить с перезагрузкой после первого обрыва: точный запрос
   остаётся доступным для повтора в профиле. Не создавать новый выбор вместо
   повтора прежнего. Серверное место/закладка уже могут быть сохранены, хотя
   клиент ещё не получил подтверждение.

`test_reading_journey.py` проверяет реальное закрытие TCP для всех четырёх
маршрутов, точное тело повтора, независимость режимов/адресов, совместное
включение и одноразовость при параллельных запросах. Его upstream технический;
успешные автотесты прокси не означают приёмку этого пути в браузере с API/БД.
Полный обрыв сети, истечение входа и физические телефоны проверяются отдельно.

### Недоступный API и истечение входа во время чтения

```sh
python3 scripts/reading_journey.py --interactive-faults
```

После готовности ввести команду в терминале стенда и нажать Enter:

| Команда | Действие |
|---|---|
| `offline a` / `online a` | Отключить / вернуть API для `127.0.0.1:4311` |
| `offline b` / `online b` | Отключить / вернуть API для `localhost:4312` |
| `expire` | Сделать истёкшими все текущие сессии только в одноразовой БД этого запуска |

`offline` закрывает соединение до обращения к API; приложение и книги остаются
доступны по HTTP. Команда действует на новые запросы, уже отправленные запросы
не отменяет. Это проверка недоступного API, а не полного отключения сети устройства.
Другой frontend независим. `online` не восстанавливает истёкший вход: нужен новый
код для того же аккаунта. Без флага stdin не читается; EOF отключает управление,
оставляя стенд работающим до Ctrl+C. Управление доступно только из терминала,
дополнительных HTTP-маршрутов нет. Можно сочетать с флагами потери ответов выше.

1. Войти на A с новым тестовым email. Открыть книгу аккаунта из профиля,
   перейти в главу 2 и поставить закладку.
2. В терминале выполнить `offline a`. Нажать «Сохранить и выйти»:
   приложение должно сообщить об ошибке и сохранённых местных данных,
   предложить повтор и выход с местом на устройстве.
3. Выполнить `online a`, нажать «Повторить сохранение». Должен открыться
   профиль без ожидающих изменений, с главой 2 и одной закладкой в аккаунте.
4. Открыть книгу снова, удалить закладку главы 2, перейти в главу 3.
   Выполнить `expire`, затем «Сохранить и выйти». Должно появиться сообщение
   об истёкшем входе; новая позиция и удаление остаются на устройстве.
5. Выйти с местным местом, заново войти тем же email (учитывая минутный лимит
   отправки кода). В профиле должно остаться по одному ожидающему изменению
   места и закладки; в аккаунте пока глава 2 и прежняя закладка.
6. Через сравнение явно сохранить место устройства и удалить закладку аккаунта.
   Ожидающих изменений больше нет; повторное открытие книги показывает главу 3
   и ноль закладок. Гостевая закладка остаётся отдельно.
7. Для проверки на B войти тем же аккаунтом: серверная глава 3, закладок нет.
   Отдельно повторить с reload между ошибкой и восстановлением и с полным
   отключением сети устройства.

Автоматические Python-проверки подтверждают независимость управления клиентами,
закрытие настоящего TCP до отправки upstream и успешное возвращение проксирования,
включая совместимость с потерей ответа после commit. Шаги интерфейса проверяются
вручную; этот стенд не заменяет HTTPS и физические Android/iPhone.

### Перезагрузка между ошибкой сохранения и продолжением на другом клиенте

```sh
python3 scripts/reading_journey.py --drop-first-save-response --interactive-faults
```

Использовать новый `@example.test` аккаунт для каждого запуска; A и B — адреса
стенда выше. Не переносить гостевое место перед шагом 2: его сохранение расходует
первый обрыв ответа позиции. Достаточно скопировать гостевую полку.

1. На A открыть книгу из полки аккаунта, перейти в главу 2, добавить закладку.
2. Нажать «Сохранить и выйти». После ошибки потери ответа **перезагрузить
   страницу**, не нажимая повтор. Сервер уже принял место, но клиент ещё не
   подтвердил его. Читалка должна показать незавершённое сохранение и ссылку
   в профиль; выбор места аккаунта до проверки недоступен.
3. В профиле проверить по одному ожидающему месту и изменению закладки.
   Открыть незавершённое сохранение места и повторить прежний выбор. Счётчик
   места должен обнулиться, закладка пока остаётся ожидающей.
4. Сравнить и сохранить закладку. После потери её ответа снова перезагрузить
   страницу. Должны остаться одно незавершённое сохранение закладки и кнопка
   его открытия, даже если серверная закладка уже совпадает с местной.
   Открыть его и повторить выбранное изменение: ожиданий больше нет.
5. Войти тем же email на B, открыть книгу из полки аккаунта. Ожидаются глава 2
   и ровно одна закладка. Удалить её и перейти в главу 3.
6. Выполнить `offline b`, нажать «Сохранить и выйти», после ошибки перезагрузить
   страницу. Ожидается сообщение о невозможности проверить вход. Это ограничение
   текущего офлайн-входа аккаунта, а не подтверждение утраты местных данных.
7. Выполнить `online b`, перезагрузить страницу. Должны предлагаться местная
   глава 3 и серверная глава 2. Перейти в профиль: там по одному ожидающему
   месту и удалению. Явно сохранить местное место и удаление закладки.
   Первый успешный ответ каждого сохранения на B тоже будет потерян;
   повторить прежний выбор. Очередь должна очиститься.
8. Перезагрузить A и открыть книгу аккаунта. Выбрать продолжение с места
   аккаунта: глава 3, закладок нет. Гостевая закладка A остаётся отдельно.

До остановки стенда проверить SQL в **одноразовой БД этого запуска** (имя
`journey_…`, не рабочая `lumyboo`). Для нового аккаунта и ровно этих действий:

```sql
SELECT book_id, server_revision, locator FROM reading_positions;
SELECT book_id, server_revision, deleted_at IS NOT NULL AS deleted FROM bookmarks;
SELECT count(*) AS archived_positions FROM reading_position_history;
```

Ожидаются одна позиция главы 3 с ревизией 2, одна удалённая закладка с ревизией 2
и одна архивная позиция. Повторы после потери ответа не повышают ревизии.
Количество receipts времени/покрытия зависит от длительности чтения и не служит
фиксированным критерием этого прогона. Проверку истечения входа, полного
отключения сети устройства и физические телефоны выполнять отдельно.

### Смена аккаунта с неотправленными местом и закладкой

Запустить `python3 scripts/reading_journey.py --interactive-faults`. Использовать
один frontend (`127.0.0.1:4311`) и два новых тестовых email `@example.test`.
Здесь A/B обозначают аккаунты, а терминальная команда `offline a` управляет
frontend. Не копировать гостевые закладки или место: они проверяются отдельно.

1. Войти в аккаунт A, скопировать гостевую полку с тестовой книгой «Комната для
   историй». Открыть её из полки аккаунта: глава 1, закладок нет. Перейти в
   главу 2 и поставить закладку.
2. Выполнить `offline a`, нажать «Сохранить и выйти». Проверить сетевую ошибку
   и сообщение о местном сохранении; выбрать «Выйти с местом на устройстве».
3. Выполнить `online a`, перезагрузить профиль. После автоматической отправки
   времени/фрагментов должны остаться одно место и одно изменение закладки.
   Выйти из аккаунта: должно появиться предупреждение о локальных изменениях.
   Подтвердить выход с сохранением изменений на устройстве.
4. Войти в аккаунт B в том же браузере. Его полка и серверные закладки пусты,
   ожидающих изменений нет. Место A не отображается как место B; отдельно
   подписанное гостевое место может предлагаться для явного переноса.
5. Через «Открыть в читалке аккаунта» открыть ту же книгу. Ожидаются глава 1
   и ноль закладок. Перейти в главу 3, поставить закладку, сохранить и выйти.
   Проверить совпадение мест главы 3, одну серверную закладку «Комната» и
   отсутствие ожидающих изменений. Выйти из B.
6. Снова войти в A. Должны вернуться одно ожидающее место главы 2 и одно

   Открыть книгу: глава 2 и одна местная закладка. Нажать «Сохранить и выйти»:
   место сохраняется, а прежнее изменение закладки требует сравнения в профиле.

   Очередь должна очиститься. После reload место и закладка A остаются в главе 2.
   Гостевая закладка остаётся отдельно. Сохранение A не меняет данные B.

Перед остановкой стенда выполнить в одноразовой БД этого запуска (`journey_…`):

```sql
SELECT i.email, p.book_id, p.server_revision, p.locator
FROM reading_positions p JOIN auth_identities i USING (user_id)
ORDER BY i.email;
SELECT i.email, b.server_revision, b.locator, b.deleted_at
FROM bookmarks b JOIN auth_identities i USING (user_id)
ORDER BY i.email;
```

Для этих действий ожидаются две позиции и две неудалённые закладки: A — глава 2
(`chapter: 1`, `ch-2-p-1`), B — глава 3 (`chapter: 2`, `ch-3-p-1`); каждая с
ревизией 1 и своим владельцем. Смещение места зависит от прокрутки; закладки
ставятся в начале главы. Это проверка последовательной смены аккаунтов на одном
origin с настоящими API/БД. Смена аккаунта в другой открытой вкладке, потеря
ответа logout, полный offline, HTTPS и физические телефоны проверяются отдельно.

### Потеря ответа входа/выхода и другая вкладка

`auth-tabs.test.ts` проверяет уведомление второй вкладки после сетевого отказа

### Две вкладки: ответ входа потерян целиком, включая cookie

```sh

```

Использовать новый тестовый email и две вкладки одного origin
`http://127.0.0.1:4311`, без действующей сессии в одноразовой БД.
Обновить приложение перед началом. Уже открытый аккаунт этим путём не проверяется.

2. В первой ввести код. Журнал стенда должен показать
   `Lost successful response: ... path=/api/v1/auth/verify`.

   вторая без reload остаётся с предложением войти. Сбой не должен ни
   открывать аккаунт, ни создавать видимость успешного входа.

   verify уже не должен теряться. Первая вкладка открывает профиль этого
   аккаунта, вторая без reload — главу 1 с нулём закладок. Никакие прежние

### Диагностика первой загрузки профиля после восстановления входа

При редкой ошибке «Места чтения аккаунта» повторить предыдущий путь с диагностикой:

```sh
python3 scripts/reading_journey.py --drop-first-verify-response before-headers --trace-api
```

После нового OTP сначала зафиксировать состояние раздела **до** нажатия
«Повторить загрузку». Сопоставить `/api/v1/positions/` и `/api/v1/auth/session`
в JSON-строках `event=journey_api`: frontend, метод, путь без query, статус
ответа API, `requestId`, время и `outcome`. Диагностика выключена по умолчанию;
тела запросов/ответов, cookie, заголовки авторизации и query в эти строки не входят.

- `delivered`: прокси закончил запись ответа в сокет; это ещё не доказывает,
  что браузер прочитал и отрисовал данные. Для HTTP-ошибок проверить `status`.
- `client_disconnected`: ошибка записи браузеру после начала передачи ответа.
  Прокси закрывает соединение, не дописывая второй ответ 502 к первому.
- `upstream_error`: ошибка соединения с API или чтения его ответа; прокси
  пытается вернуть 502. `status` может отсутствовать или содержать уже полученный
  статус API; это не статус локального 502.
- `injected_response_loss`, `injected_body_loss`, `injected_offline`: явно
  включённый сбой стенда; не считать его самостоятельной ошибкой API.
- `rejected_request`: прокси отклонил недопустимый размер тела с 413.

Если ошибка появилась, сохранить эти строки и точное сообщение интерфейса
перед повтором. HTTP 200 в журнале без успешного раздела не закрывает проверку.
Отсутствие повторного сбоя также не устанавливает причину прежнего наблюдения.
Тесты стенда проверяют разделение ошибки API и отмены браузером, отсутствие
второго ответа после обрыва записи, opt-in и исключение секретов из трассировки;
TCP-проверка потери ответа остаётся отдельной частью этого набора.


### Потеря ответа при смене уже открытого аккаунта: HTTPS/API

`TestPostgresAccountSwitchWithLostVerifyReply` проверяет настоящий обрыв TLS-
соединения после успешного выполнения `/auth/verify` в PostgreSQL. Перед сбоем
первая сессия вошла в A и сохранила место главы 2 и закладку; независимая сессия
того же A остаётся открытой. Затем первая сессия отправляет настоящий код B.

- `before-headers`: новая cookie не доставлена, прежняя сессия A уже отозвана.
  Получение сессии, мест и закладок возвращает 401. Повтор использованного кода
  отклонён; восстановление выполняется новым OTP B. Перед сдвигом ограничения
  повторной отправки в одноразовой схеме проверяется 429.
- `after-headers`: получены Set-Cookie и HTTP 200, тело оборвано с исходным
  Content-Length. Cookie jar принимает cookie B; последующий GET сессии
  подтверждает B, его места и закладки пусты.

В обоих вариантах повтор старого кода не создаёт доступ, прежняя cookie A
не открывает отозванную сессию. Независимая сессия A всё ещё получает исходное
место и закладку. Тест использует общий HTTPS-стенд предыдущего раздела,
настоящие OTP/API/БД и тестовый почтовый ящик; разрыв выполняется сервером через
hijack соединения, без подмены ошибки HTTP-клиента. Сертификату доверяет только
тестовый клиент, системное доверие не меняется.

Это проверка протокола и изоляции серверных данных. Она не заменяет проверку
React-интерфейса и уведомлений двух браузерных вкладок, публичного HTTPS-стенда,
Android/iPhone или установленной PWA при смене уже открытого аккаунта.


### Две вкладки: A → выход → B → выход → A с потерей ответа входа

Запустить `python3 scripts/reading_journey.py --interactive-faults --trace-api`.
Обе вкладки открывать на `http://127.0.0.1:4311`; второй frontend использует
`http://localhost:4312` и отдельный origin, он не заменяет соседнюю вкладку.
Команда терминала `lose-verify a after-headers` или
`lose-verify a before-headers` включает потерю **следующего успешного**
ответа входа только на frontend A. Можно включить её после обычного входа;
неуспешные запросы не расходуют сбой. Команда может повторно включить сбой.
Она доступна только в одноразовом стенде с `--interactive-faults`, HTTP-пути
управления и изменения продуктового API не добавляются.

1. Войти в новый A обычным OTP из Mailpit. Во второй вкладке открыть
   «Комнату для историй» через «Открыть в читалке аккаунта», выбрать главу 2,
   поставить закладку. Первую вкладку оставить в профиле.
2. Выйти из A в первой вкладке, выбрав сохранение изменений на устройстве.
   Вторая вкладка без reload должна убрать текст и предложить войти.
3. В терминале выполнить `lose-verify a after-headers`, затем войти в новый B.
   Журнал должен показать `injected_body_loss` для verify и успешные GET сессии.
   Первая вкладка подтверждает email B; вторая без reload открывает главу 1
   с нулём закладок. Закладка и глава A в B не появляются.
4. Выйти из B с сохранением изменений на устройстве. Включить
   `lose-verify a before-headers`, запросить код A и отправить его.
   Журнал должен показать `injected_response_loss`; первая вкладка сообщает
   сетевую ошибку, вторая не открывает текст. Повтор использованного кода
   отклоняется. Ни A, ни B не должны получить доступ без подтверждённой сессии.
5. Дождаться штатной доступности повторной отправки, получить новый OTP A
   и войти. Вторая вкладка без reload возвращает главу 2 и одну закладку A.
   Гостевая закладка остаётся отдельно. Не сдвигать resend gate и не подставлять
   cookie при браузерной проверке.

Это путь через обычный выход в UI: Login скрывает форму при действующей
сессии. Он дополняет HTTPS-тест прямой замены действующей cookie A на B,
описанный выше. Проверка на loopback не подтверждает публичный HTTPS,
физические устройства или установленную PWA. Дополнительная статистика из
незавершённых локальных изменений не является предметом этого сценария.

Проверка команды включения:

```sh
python3 -m unittest discover -s scripts -p test_reading_journey.py
```

Набор проверяет изоляцию frontend, повторное включение обоих режимов,
конкурентную однократность, отказ неизвестных команд и настоящий TCP-обрыв
с доставкой/без доставки Set-Cookie.


### Занятое сохранение времени в другой вкладке

```sh
npm test --workspace apps/web -- src/lib/reading-time-auto.test.ts src/lib/reading-session-sync.test.ts src/lib/reading-coverage-sync.test.ts src/lib/reading-coverage-receive-auto.test.ts src/lib/api.test.ts
```

При занятом Web Lock автоматический отправитель показывает ожидание другой
вкладки, затем через 5 секунд заново проверяет очередь. Занятость не считается
сетевым сбоем и не увеличивает счётчик backoff. Сетевые ошибки по-прежнему
показывают ошибку и повторяются с задержкой; 401/403, конфликт и неверное
подтверждение останавливают отправку. Общая обработка применяется к времени,
отправке и получению фрагментов; ожидание получения не объявляет его успешным.

Регрессия в `reading-session-sync.test.ts` использует два подключения к одной
fake-indexeddb, настоящие Node Web Locks и продуктовый отправитель с управляемым
fetch: первая вкладка удерживает ответ последней записи, вторая обнаруживает
занятость. После подтверждения первая удаляет операцию; вторая проверяет пустую
очередь без второго POST и повторной проверки входа. Локальное время сохраняется.
Тесты планировщика отдельно проверяют backoff после занятости и сетевой ошибки.

Для браузерной проверки открыть один тестовый аккаунт в двух вкладках одного
origin и задержать ответ `/reading-sessions/apply` в одноразовом стенде.
Пока первая вкладка сохраняет, вторая показывает ожидание другой вкладки.
После подтверждения и следующей проверки очереди сообщение меняется на обычный
статус автосохранения. Повторить для фрагментов. Этот сценарий дополняет проверку
A → B → A выше; автотесты не устанавливают причину прежнего браузерного эпизода
без захвата занятого lock или сетевой ошибки в момент его появления.


### Два автоматических отправителя времени с настоящими API/PostgreSQL

В первом терминале запустить одноразовый стенд без инъекции потерь:

```sh
python3 scripts/reading_journey.py --trace-api
```

После сообщения о готовности API во втором терминале из корня репозитория:

```sh
VITE_LUMYBOO_LIVE_TEST=1 npm test --workspace apps/web -- src/lib/reading-time-live.test.ts
```

Тест намеренно привязан к loopback `127.0.0.1:4311` и Mailpit `127.0.0.1:8025`.
Нужны Docker/PostgreSQL и SMTP из инструкции стенда. Обычный `npm test` пропускает
этот тест; флаг включать только с запущенным `reading_journey.py`. Тест создаёт
уникальные `@example.test` аккаунты, стенд удаляет их вместе с одноразовой БД
по Ctrl+C. Срок действия OTP и интервал повторной отправки не меняются;
возврат в A ждёт штатного интервала, поэтому прогон занимает около минуты.

Проверяются продуктовые `startReadingTimeAuto`, `sendReadingSessions`, HTTP-клиент
и история времени с настоящими OTP/SMTP/API/PostgreSQL:

- После фиксации первой записи сервером её ответ удерживается тестовой обёрткой
  fetch. Второй отправитель на другом подключении к той же IndexedDB встречает
  настоящий Node Web Lock и показывает ожидание другой вкладки.
- После доставки ответа очередь очищается, второй отправитель обнаруживает её
  пустой без повторного POST. В серверной истории ровно одна запись 12345 мс,
  оба отправителя обходятся без сообщения ошибки сохранения.
- Более поздний локальный снимок A остаётся в очереди при выходе и входе в B.
  Отправитель A с cookie B останавливается до POST; история B сначала пуста.
  B сохраняет собственные 4000 мс.
- После обычного выхода B и нового OTP A его снимок отправляется автоматически.
  Серверная история A содержит одну запись 20000 мс, а локальный счётчик сохраняет
  20 секунд. За весь прогон выполнены три POST времени.

Тестовая среда Node использует fake-indexeddb, настоящий Node LockManager и
обёртку fetch для относительных URL, Origin и cookie. Обёртка не заменяет ответы
API; блокируется только доставка одного ответа. Это интеграционная проверка
отправителей и серверных данных. React, BroadcastChannel, браузерные cookie,
настоящий IndexedDB, публичный HTTPS и физические устройства ею не проверяются;
двухвкладочный UI-прогон A → B → A остаётся отдельной проверкой выше.


### Первый запрос скачанной книги при отключённой сети

```sh
npm test --workspace apps/web -- src/lib/books.test.ts src/lib/reading-ownership.test.ts src/lib/pwa.test.ts
```

`bookQueryOptions` используется читалкой и превью текста при сравнении мест и
закладок. Запрос запускается при отключённой сети: `loadBook` сначала проверяет
загруженный текст в Cache Storage. Сам запрос не должен ждать подключения до
первой проверки локальной копии. Общие настройки исключают создание запроса
с тем же ключом `book` и иной сетевой политикой из соседнего превью.

Регрессионный тест сохраняет проверенную книгу, переоткрывает IndexedDB,
создаёт новый QueryClient/QueryObserver и устанавливает onlineManager в offline.
Он ожидает успешный результат с текстом и отсутствие fetch. До исправления
этот путь оставался pending с приостановленным запросом, хотя `loadBook` напрямую
мог прочитать скачанный текст. Дополнительные случаи утраченной/повреждённой
копии проверяют переход в ошибку, удаление неверного признака загрузки и успешный
явный refetch после восстановления сети. Проверки используют fake-indexeddb
и модель Cache Storage; Service Worker и настоящий браузер в них не участвуют.

Для ручной приёмки гостя: скачать полную книгу при подключении, дождаться
готовности оболочки, полностью закрыть PWA, включить авиарежим и открыть PWA
заново. Перейти к книге, которую ещё не открывали в текущем сеансе приложения:
текст должен появиться без ожидания сети. Проверить главу, закладку, сохранение
и повторный запуск. Затем отдельно проверить утрату/повреждение загрузки и
повтор после восстановления сети. Выполнить на Android и iPhone. Эта проверка
остаётся открытой; исправление запроса не подтверждает полный офлайн-сценарий.
Для аккаунта по-прежнему нужна проверка входа: политика запроса публичного текста
не заменяет AccountReaderGate и не предоставляет офлайн-доступ к данным аккаунта.

## Перенос гостевой дневной цели

На временном стенде `python3 scripts/reading_journey.py` выбрать гостю 5 минут
на завтра, войти уникальным `@example.test` адресом и открыть в профиле
«Перенести гостевую цель». Сравнить показанные цели; «Оставить цель аккаунта»
не меняет её. Подтверждение ставит гостевую цель с завтрашнего дня аккаунта;
сегодняшняя цель и гостевые данные сохраняются. Перезагрузить профиль.
Раннюю историю можно включить отдельно: только до первого сохранённого дня
аккаунта и при совпадении часового пояса. Если аккаунт уже читал до настройки
цели, сервер отклоняет добавление истории; снять выбор истории и повторить.
Гостевые минуты, серия, место и закладки этим действием не переносятся.

`npm run test -w apps/web -- src/lib/account-daily-goal.test.ts src/lib/daily-goal.test.ts`
проверяет выбор, неизменность повтора и конфликт после просмотра.
На отдельной тестовой PostgreSQL:
`TEST_DATABASE_URL=… go -C services/api test ./internal/httpapi -run 'TestPostgres(GuestGoal|DailyGoal)'`
проверяет исторические цели, доступ и сохранность прежних дней. Тесты создают
собственные схемы, применяют миграции и удаляют схемы после завершения.

## Явный перенос гостевого времени

1. Прочитать книгу гостем, сохранить и выйти. Войти в тестовый аккаунт, открыть профиль → «Перенести гостевое время».
2. Проверить даты, время, исторические цели гостя/аккаунта и часовые пояса. Дни изначально не выбраны. Закрыть окно: время и цели аккаунта не изменились.
3. Выбрать день и подтвердить добавление по целям аккаунта. Обновлённый подтверждённый итог учитывает гостевые записи, локальное время аккаунта не увеличивается. Гостевые записи и очередь сохраняются.
4. Повторить выбор того же дня после reload: итог не удваивается. Продолжить гостевую сессию и перенести снова: принимается только увеличение накопленного времени исходной сессии.
5. На стенде `python3 scripts/reading_journey.py --drop-first-reading-response` первый ответ сохранения теряется после записи в БД. Повторить сохранённый выбор в окне либо после его закрытия/перезагрузки. Итог остаётся прежним. Отмена дальнейших повторов не откатывает уже принятое сервером время.
6. При разных целях подтвердить, что сохраняется история целей аккаунта. Если цель аккаунта изменилась после просмотра, новый перенос останавливается: нужно открыть сравнение заново. При разных часовых поясах окно явно предупреждает, что сохраняются гостевые даты без пересчёта; можно оставить данные отдельно.
7. Проверить смену аккаунта перед отправкой: выбор A не отправляется в B. Сохранённый незавершённый выбор остаётся в базе A. При более 50 сессий выбранных дней кнопка продолжения отправляет следующую часть. Старые записи без издания/устройства остаются локальными, их происхождение не угадывается.

Профильные web-тесты: `npm run test -w apps/web -- src/lib/guest-time-import.test.ts src/lib/reading-session-sync.test.ts src/lib/account-daily-goal.test.ts src/lib/daily-goal.test.ts`. Серверный перенос использует существующий `/reading-sessions/apply`: исходный session ID и накопленный максимум вместо сложения snapshots. `TestPostgresReadingSessions` проверяет настоящий PostgreSQL, повторы, увеличение, конкурентные snapshots и изоляцию владельцев. Перенос не меняет цели, место, закладки, покрытие и награды; серия рассчитывается по принятому времени и историческим целям аккаунта.

## Краткий итог после чтения

1. Открыть книгу гостем, почитать, сменить главу и открыть/закрыть настройки. Нажать «Сохранить и выйти» или верхнюю кнопку закрытия: после локального сохранения появляется «Время для себя.». Время текущего открытия книги показано отдельно от всего времени дня, включая другие книги. «Готово», Escape и закрытие окна завершают выход; время при открытом итоге не растёт.
2. Повторно открыть книгу и сразу выйти: новое чтение начинается с нуля, прежние минуты входят только в итог дня. После выполнения порога показано «Дневная цель выполнена». Порог и смена суток проверяются профильными тестами без ожидания нескольких минут в браузере.
3. В аккаунте проверить отдельные значения «На этом устройстве» и «Итог аккаунта». До принятия очереди серверный итог может быть меньше локального. Он обновляется при изменении очереди и по кнопке; значения не складываются. Ошибка обновления сохраняет локальный результат и позволяет завершить выход. Для ранее открытого локального доступа без сети серверный результат не запрашивается и не объявляется подтверждённым.
4. При ошибке сохранения места/закладок аккаунта остаётся прежнее окно ошибки с повтором или выходом с местом на устройстве. При ошибке локального сохранения успешный итог не показывается. Проверить оформление Blanc/Noir в компактной рамке, прокрутку длинного аккаунтного итога и доступность «Готово».
5. При чтении через полночь время текущего открытия делится по исходным дням; цель и прогресс сегодня используют сохранённый часовой пояс владельца и историческую цель. Итог не отмечает книгу прочитанной и не начисляет XP/заморозки.

Профильные проверки: `npm run test -w apps/web -- src/lib/reading-summary.test.ts src/lib/reading-session-recorder.test.ts src/lib/daily-goal.test.ts`. Проверяются только подтверждённые локальной записью snapshots текущего recorder, максимум повторов, разделение сессии и итога дня, полночь, исторические цели и изоляция гостя/аккаунта.

## Создание закрытого челленджа

Перед обновлением API применить миграцию `011_challenges.up.sql` по обычной процедуре миграций. Она добавляет условия челленджа и запись его создателя; без неё readiness возвращает 503. При откате этой миграции удаляются созданные челленджи и их участники.

```sh
npm run test -w apps/web -- src/lib/challenges.test.ts
TEST_DATABASE_URL='postgres://lumyboo:local-development-only@127.0.0.1:5432/lumyboo?sslmode=disable' \
  go -C services/api test -race ./internal/httpapi -run 'Challenge|Readiness'
```

PostgreSQL-тесты создают отдельную схему, применяют все миграции и удаляют только эту схему. Без `TEST_DATABASE_URL` они пропускаются. Проверяются создание обоих форматов, фиксированные условия, параллельный/поздний повтор, изоляция аккаунтов, Origin, CSRF и отклонение неверных условий. Web-тесты проверяют неизменный повтор после потери ответа/перезагрузки модуля, смену аккаунта и отказ локального хранилища до отправки запроса.

## Подтверждённый прогресс закрытых челленджей

Перед обновлением API применить `013_challenge_progress.up.sql`: readiness требует новую колонку. Она сохраняет дни участника при выходе. Для вышедших до обновления фиксируются имеющиеся на момент миграции суммы по датам до выхода; восстановить прежние промежуточные снимки невозможно. Откат удаляет снимки выхода, но не обычное время чтения.

```sh
npm run test -w apps/web -- src/components/ChallengeProgress.test.tsx src/lib/challenges.test.ts
TEST_DATABASE_URL='postgres://lumyboo:test@127.0.0.1:55433/lumyboo?sslmode=disable' \
  go -C services/api test -race -count=1 ./internal/httpapi -run 'TestPostgres(Challenge|Challenges|Readiness)'
```

Тесты проверяют оба формата, точный порог в миллисекундах, несколько сессий/устройств, повтор и меньший поздний снимок, дополнение прошедшего дня, границы периода и текущего дня в общем поясе при DST. Обычная дневная цель не меняет цель челленджа. Выход фиксирует принятые дни; последующие отправки не меняют этот снимок. Отдельно проверены миграция прежних вышедших участников, readiness без колонки, приватность и одинаковые псевдонимы.

Чтение считается по исходным датам сессий, без пересчёта между поясами; предупреждение показывается в условиях создания/вступления и прогрессе. Общий пояс определяет текущую дату и границы периода. Участникам доступны выполненные дни команды и своё подробное время; книги, почта и чужие ежедневные длительности скрыты. Поздние записи могут дополнять результаты продолжающих участие, включая завершённый период. Прошедший срок не означает выполнение; итоговые места рассчитываются отдельным шагом.

Браузерная проверка: открыть челлендж с несколькими участниками и принятыми сессиями, раскрыть «Твои дни и время», проверить свой порог и дни команды; обновить после отправки с другого устройства. После выхода убедиться, что новые сессии не меняют сохранённые дни. Проверить Blanc/Noir и прокрутку внутри компактной рамки. Компонентный предпросмотр с фикстурой проверяет отображение, а не заменяет приёмку двух реальных устройств.

Для браузерной проверки запустить `python3 scripts/reading_journey.py`, войти через код из Mailpit и открыть «Вместе»:

1. Создать соревновательный челлендж с общей целью, будущей датой старта и общим часовым поясом. Проверить сохранённые название, псевдоним, цель и длительность.
2. Создать личностный челлендж с другой целью. Здесь пояснение не обещает рейтинг между участниками.
3. Перезагрузить приложение: оба челленджа сохраняют свои условия. Открыть другой аккаунт: его список пуст.
4. Проверить форму и карточки в Blanc/Noir. После неоднозначной ошибки сохранения повторять сохранённый запрос кнопкой «Повторить создание»; он хранится в `sessionStorage` отдельно для аккаунта и сохраняется при перезагрузке вкладки. Закрытие вкладки не гарантирует сохранения неподтверждённого запроса.

Этот путь проверяет создание и получение собственных челленджей. Приглашения, вступление, выход, подсчёт выполненных дней и итоговые места в него не входят. Создание записи не подтверждает прохождение совместного сценария на двух устройствах.


## Приглашение, вступление и выход из челленджа

До обновления API применить `012_challenge_invitations.up.sql`. Readiness проверяет таблицу приглашений и поле выхода. Откат удаляет коды и признаки выхода; использовать его до открытия приглашений пользователям либо после сохранения данных и остановки записи.

Профильные команды из раздела выше включают тесты приглашений. PostgreSQL-проверки покрывают приватный просмотр условий, оба формата целей, повтор вступления/выхода, отзыв и замену кода, лимит 10 при параллельном вступлении, границу старта, CSRF и смену аккаунта. Web-тесты дополнительно проверяют владельца ответа и повтор действия после потери ответа.

На временном стенде `python3 scripts/reading_journey.py`:

1. На клиенте A войти в аккаунт, создать челлендж с будущим стартом и показать код приглашения. Скопировать код. Его передача другу — ручное действие пользователя, приложение не отправляет сообщения.
2. На клиенте B войти в другой аккаунт, выбрать «Вступить по коду», ввести код и посмотреть условия. До вступления список участников не раскрывается. Принять условия со своим псевдонимом; в личностном формате выбрать свою цель. В соревновательном цель берётся из условий независимо от значения в запросе.
3. Обновить список A и перезагрузить B: оба видят команду, псевдонимы и фиксированные цели, без почты, книг и ID других аккаунтов.
4. На A отозвать приглашение. Новый аккаунт больше не может посмотреть условия или вступить по старому коду. Уже вступившие остаются; повтор прежнего вступления не создаёт новую запись. Новый показ приглашения выдаёт новый код.
5. На B подтвердить выход: запись участия остаётся с отметкой «вышел». Повтор вступления не возвращает пользователя в команду. Выход создателя также отзывает активное приглашение, сохраняя остальных участников.
6. Проверить Blanc/Noir и компактную рамку. Наступление дня старта в общем часовом поясе закрывает новые вступления; вступивший ранее может восстановить результат запроса.

Приглашение не добавляет друзей и не открывает переписку. Выполненные дни, места и итог периода проверяются отдельно после реализации командного прогресса. Проверка двух браузерных клиентов не заменяет приёмку D на физических устройствах.


## Места и итог периода в челлендже

```sh
npm run test -w apps/web -- src/components/ChallengeProgress.test.tsx src/lib/challenges.test.ts
cd services/api
TEST_DATABASE_URL='postgres://…' go test -race ./internal/challenges ./internal/httpapi -run 'TestCompetitionPlaces|TestPostgresChallenge|TestReadiness'
```

Место вычисляет API только в соревновательном формате после старта: один плюс число участников с большим количеством выполненных дней. Ничьи дают места 1, 1, 3; минуты сверх цели не используются. Учитываются сохранённые результаты вышедших участников. До старта и в личностном формате поле `rank` не передаётся. Завершение периода не означает выполнение цели. Поздние принятые сессии продолжающих участие могут изменить итог и места; результат вышедшего остаётся снимком на момент выхода.

В браузере проверить текущие и завершённые места, ничью, отсутствие выполненных дней и выполнение всех дней. После поздней синхронизации обновить список с двух аккаунтов: места должны совпадать. Проверить отсутствие рейтинга в личностном формате, отметку выхода и отсутствие чужого времени по дням, почты и книг. Повторить в Blanc/Noir внутри компактной рамки; предпросмотр на фикстуре не заменяет этот сценарий с настоящими аккаунтами.

## Просмотр интерфейса с телефона по локальному HTTP

При запуске preview с `--host 0.0.0.0` открыть адрес компьютера в той же Wi-Fi
сети. Этот origin не даёт CacheStorage, SubtleCrypto, Web Locks и service worker.
Проверить переключение темы, сохранение настроек, добавление на полку и reload:
локальные операции используют UUID из криптографически случайных байтов даже
при отсутствии `crypto.randomUUID`. Проверка загрузок не должна удалять метаданные
или показывать ошибку отсутствующей переменной `caches`. Чтение/скачивание должны
объяснять необходимость HTTPS. Этот просмотр не заменяет HTTPS-приёмку чтения,
аккаунтов и установленной PWA.

## Чтение из каталога и главной после входа

`npm run test -w apps/web -- src/pages/Library.test.tsx` проверяет маршрут чтения,
выбор цели и отсутствие прежнего места при смене владельца/книги. При проверке
входа действие заблокировано; ошибка без локального разрешения ведёт в профиль.

На одноразовом стенде выше:

1. Оставить гостю место и закладку. Войти, открыть карточку через каталог:
   «Читать в аккаунте» ведёт в `/account/read/...`; гостевая глава не показана
   как место аккаунта. Главная использует цель аккаунта.
2. В аккаунтной читалке перейти к другой главе, поставить закладку, сохранить
   и выйти. На втором адресе войти тем же email; открыть книгу с главной или
   из каталога. Глава и закладка загружаются из аккаунта.
3. Изменить главу во втором клиенте, сохранить, снова открыть книгу в первом.
   Различающиеся места устройства/аккаунта требуют явного выбора. Принять
   аккаунтное: открывается новая глава, закладка сохранена.
4. Выйти из аккаунта в первом клиенте. Карточка снова ведёт в `/read/...`,
   показывает прежнее гостевое место. Гостевая цель и закладки остаются отдельно.

Эта проверка двух origins на одном компьютере не заменяет HTTPS и телефоны.
