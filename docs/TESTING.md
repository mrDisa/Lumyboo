# Проверка чтения и обновления PWA

## Автоматические проверки

```sh
npm ci
npm test
npm run build
node scripts/check-content.mjs
python3 -m unittest discover -s scripts -p 'test_*.py'
```

Сборка дополнительно проверяет, что все UI JS/CSS/шрифты/изображения попали в precache ровно один раз, код Workbox включён в сам worker, а тексты книг и API не кешируются как оболочка.

Веб-тесты проверяют данные IndexedDB, переход схемы v1 → v2, историю позиции прежнего издания, чтение проверенного текста из Cache Storage после повторного открытия базы, обрыв повторной загрузки, повреждение/удаление кеша, digest и структуру текста. Тесты жизненного цикла PWA проверяют однократную регистрацию и защиту открытой читалки от обновления, активированного в другой вкладке. Эти тесты не заменяют браузерную проверку service worker.

## Первая установка и запуск без сети

Использовать production-сборку: `npm run preview`. В dev-режиме worker отключён.

1. Открыть `/settings` на новом локальном порту или в чистом профиле браузера. Дождаться «Приложение сохранено на устройстве».
2. Открыть каталог, карточку тестовой книги, скачать и дождаться кнопки удаления загрузки. Прогресс 100% возможен только после проверки размера, SHA-256 и структуры.
3. Остановить preview-сервер, не открывая читалку заранее. Открыть её из карточки: это проверяет не только текст книги, но и ленивый chunk читалки.
4. Перейти во вторую главу, поставить закладку, перезагрузить страницу. Глава и закладка должны восстановиться при остановленном сервере.
5. Открыть новую вкладку с прямой ссылкой `/read/room-for-stories`. Она должна запуститься без сервера и восстановить данные.
6. Открыть `/downloads`, прочитать текст, удалить только загрузку. Позиция и закладки остаются. Попытка читать удалённый текст без сети показывает понятную ошибку.

Повторить на настоящих Android и iPhone, в установленной PWA и авиарежиме. Проверить закрытие браузера/приложения, перезапуск телефона, нехватку места и очистку браузером кеша. Localhost компьютера не доступен телефону как localhost — нужен HTTPS-стенд.

## Обновление приложения

1. Открыть читалку в первой вкладке и каталог во второй.
2. Собрать изменённую версию приложения, перезагрузить только вторую вкладку, дождаться предложения обновить.
3. Применить обновление во второй вкладке. Первая вкладка с читалкой не должна перезагружаться.
4. В первой вкладке сохранить и выйти, затем явно применить обновление. После перезагрузки восстановить главу/абзац и закладки.
5. Если издание книги обновлено, прежний locator должен остаться в IndexedDB `positionHistory`; новый текст открывается с первой главы. Закладки прежней версии не должны переносить пользователя по неверным ID нового текста.

Версия схемы IndexedDB, версия книги и версия service worker — независимые вещи. Для будущих несовместимых изменений нужна дополнительная проверка нескольких одновременно открытых версий приложения.

## Одна книга в двух вкладках

Использовать две вкладки одной версии приложения на одном origin. Для dev-сборки также проверить запуск с React StrictMode. Для аккаунта нужен доступный API и вход.

1. Открыть книгу в первой вкладке. Во второй открыть ту же книгу в том же режиме гостя/аккаунта. Должны появиться сообщение о другой вкладке и кнопка повтора; текст и сравнение мест аккаунта ещё не загружаются.
2. В первой вкладке перейти к другой главе, прокрутить текст и добавить закладку. Нажать повтор во второй, пока первая читает: открытие остаётся заблокированным.
3. В первой сохранить и выйти. Во второй повторить открытие: восстановятся последнее место и закладка. В аккаунте перед продолжением заново загружаются серверные данные и при необходимости показывается сравнение мест.
4. Повторить с закрытием первой вкладки вместо выхода. После повтора вторая должна открыться; при аварийном закрытии восстанавливается последнее фактически сохранённое место.
5. Открыть другую книгу: блокировка первой ей не мешает. Гость и разные аккаунты используют отдельные блокировки и базы.
6. Повторить в production/PWA после скачивания текста без сети для гостя. Аккаунт по-прежнему требует сети для проверки входа.

`reading-ownership.test.ts` проверяет взаимное исключение, удержание блокировки до окончания финальной записи, повтор после сохранения, раздельные книги/владельцев, отменённое открытие, повторный запуск эффекта, ошибку записи и недоступный Web Locks. При ошибке финальной записи блокировка остаётся до закрытия вкладки. Поддержка Web Locks обязательна для открытия читалки; используется HTTPS или localhost. Защита действует для вкладок с этим кодом на одном origin, не заменяет серверные конфликты и не управляет вкладками со старой версией приложения.

## Точный переход к закладке

1. Открыть тестовую книгу, увеличить шрифт до 32, прокрутить до середины длинного абзаца и поставить закладку кнопкой в шапке.
2. Прокрутить дальше в той же главе. Открыть «Закладки» и выбрать сохранённую запись. Под шапкой должна восстановиться та же часть абзаца, с учётом смещения внутри него.
3. Перезагрузить страницу: место должно сохраниться. Перейти в другую главу и снова открыть эту закладку: должны восстановиться глава, абзац и смещение.
4. Открыть оглавление и выбрать уже отображаемую главу. Должен открыться её первый абзац с нулевым смещением. Повторить переход к закладке.
5. Изменить размер/начертание/интервал и проверить переход повторно. Сохраняется доля абзаца, а не прежнее число пикселей. У конца главы браузер может ограничить прокрутку доступной высотой содержимого.

Переходы внутри текущей главы и между главами используют общий механизм восстановления после загрузки шрифтов. Проверка применима к гостевой читалке и читалке аккаунта; вход и серверные места проверяются отдельно.

## Незавершённое ручное сохранение места аккаунта

`position-choices.test.ts` проверяет сохранение точного payload/operation ID в IndexedDB v4, повтор после потери ответа и открытия базы заново, запрет повтора при конфликте ревизий, истёкшую сессию, смену аккаунта, конкурирующий выбор и отказ записи. Миграция из v3 сохраняет позиции и outbox; подтверждение ручного выбора не удаляет более поздние изменения чтения.

Для ручной проверки нужны работающие API/БД и вход по почте:

1. В профиле сравнить место устройства и аккаунта. Отключить сеть перед сохранением и нажать сохранение. Закрыть диалог и перезагрузить страницу.
2. Восстановить сеть и подтвердить вход тем же аккаунтом. В разделе мест чтения открыть незавершённое сохранение: выбранная глава/абзац и прежнее место аккаунта должны соответствовать исходному сравнению. Самостоятельной отправки при входе быть не должно.
3. Повторить сохранение. Если первый запрос уже был принят, повтор должен вернуть тот же результат без дополнительной серверной ревизии. Более позднее место чтения на устройстве и его outbox должны сохраниться.
4. Изменить серверное место со второго устройства до отправки исходного выбора. Получить конфликт; после перезагрузки повтор исходного выбора должен оставаться заблокированным. Отменить выбор, дождаться загрузки мест и сравнить заново.
5. Выйти при незавершённом сохранении: должно появиться предупреждение. Войти другим аккаунтом: сохранение первого аккаунта не отображается. После возвращения в исходный аккаунт оно снова доступно.

Это сценарий ручного сохранения места. Автоматический обмен outbox и офлайн-вход в аккаунт остаются отдельными задачами. Браузерный сценарий с живым API не подтверждается одними unit-тестами.

### Открытие читалки при незавершённом сохранении

`account-reading.test.ts` проверяет потерю ответа, повторное открытие IndexedDB, выбор из другой вкладки после загрузки мест и сохранённый конфликт. До подтверждения или отмены незавершённого выбора читалка не заменяет локальное место серверным. Отказ атомарный: история, закладки, outbox и сам выбор сохраняются. Локальное чтение доступно; выбор другой книги или другого аккаунта его не блокирует.

1. Создать незавершённое сохранение по сценарию выше. Открыть ту же книгу из полки аккаунта. Должно появиться объяснение и ссылка в профиль; выбора места аккаунта быть не должно, даже если локального места ещё нет или места совпадают.
2. Продолжить с места на устройстве (либо начать с начала, если места нет). Проверить, что незавершённое сохранение по-прежнему доступно в профиле, а более позднее чтение остаётся локальным.
3. Открыть сравнение в читалке, затем создать незавершённое сохранение этой книги в другой вкладке. Попытка выбрать место аккаунта в первой вкладке должна показать ошибку. После обновления мест отображается предупреждение; данные не удаляются.
4. В профиле подтвердить прежний выбор или явно отменить дальнейшие повторы, заново открыть книгу. Выбор серверного места снова доступен, если места различаются. Отмена не откатывает уже принятое сервером изменение.
5. Повторить с конфликтом ревизий; проверить, что книги без незавершённого сохранения и другой аккаунт открываются независимо.


## Чтение при сбое загрузки данных аккаунта

`account-reading.test.ts` проверяет восстановление локального чтения после повторного открытия базы, сохранение закладок и их удалений, outbox, времени и незавершённых выборов (включая конфликт). Проверка входа выполняется заново; гостевое хранилище, другой аккаунт, истёкшая сессия, недоступная сеть, отсутствующее место, прежнее издание и невалидный locator не позволяют открыть этот режим.

1. Войти в аккаунт, открыть тестовую книгу из его полки, перейти во вторую главу, поставить закладку и сохранить место.
2. Сделать недоступным только `/api/v1/positions/` или `/api/v1/bookmarks/` (например, ответ 503 в тестовом API), оставив `/api/v1/auth/session` доступным. Заново открыть читалку аккаунта.
3. На экране ошибки нажать «Продолжить с места на устройстве». Должна восстановиться вторая глава и местная закладка. Ошибочный ответ не считается пустым списком закладок и ничего не подтверждает в очереди. Дальнейшее чтение сохраняется на этом устройстве.
4. Повторить для книги без сохранённого места этого аккаунта: показать ошибку, не начинать с гостевого места или с начала. Сохранённое место прежнего издания также не подходит.
5. Между появлением экрана ошибки и нажатием кнопки завершить сессию или сменить аккаунт в другой вкладке. Открытие прежней базы должно быть отклонено. При полном отключении сети проверка входа также должна завершиться ошибкой.
6. Восстановить API и выбрать «Попробовать снова». Обычное сравнение серверного и локального места должно снова работать.

Это восстановление при частичной недоступности API. Полноценный офлайн-вход и автоматическая синхронизация требуют отдельной реализации.

## Статус сохранения аккаунта

`account-save-status.test.ts` проверяет отдельный подсчёт мест, изменений закладок (включая удаления), записей времени и других изменений, а также приоритет конфликтов/неподтверждённых сохранений и изоляцию аккаунтов от гостя. Пустая очередь не называется синхронизированной.

`position-choices.test.ts` дополнительно проверяет подтверждение конкретных operation IDs, повтор без расширения набора подтверждаемых записей, новое чтение во время запроса, отказ локальной транзакции после серверного успеха и совместимость с ранее сохранёнными выборами без списка operation IDs.

1. Войти в аккаунт с пустой локальной очередью, открыть профиль. Блок «Сохранение данных» должен показывать «Нет изменений, ожидающих отправки».
2. Открыть читалку аккаунта, поставить закладку, читать и сохранить/выйти. В профиле должны появиться «Сохранено на устройстве» и отдельные количества мест, изменений закладок и записей времени. Гостевые изменения в этот блок не входят.
3. Явно сохранить место аккаунта в разделе ниже. Подтверждённое изменение места исчезает из счётчика; закладки и время остаются. Если чтение продолжалось после начала сохранения, новое место остаётся в очереди.
4. Повторить с потерей ответа и перезагрузкой. Блок показывает неподтверждённое сохранение; повтор отправляет прежний вариант. При конфликте показывает необходимость сравнить места заново. Отмена повтора не очищает локальные изменения.
5. Выйти и войти другим аккаунтом. Статус и счётчики должны соответствовать только текущему аккаунту. При недоступном хранилище нельзя показывать пустую очередь как успешную проверку.

## Одновременное сохранение места в нескольких вкладках

`position-choices.test.ts` проверяет блокировку повторной отправки, отмены и замены выбора из второго подключения к IndexedDB, включая период между ответом API и коммитом локального подтверждения. После сетевой ошибки исходный выбор остаётся доступным для явного повтора или отмены. Другие книги и аккаунты независимы. Без Web Locks действия завершаются ошибкой до запроса и изменения сохранённых данных; требуется HTTPS/localhost и браузер с поддержкой Web Locks.

1. Войти в один аккаунт в двух вкладках одного origin. Создать неподтверждённое сохранение места и открыть его в обеих вкладках.
2. Задержать ответ `/api/v1/positions/choose` в тестовом API. Отправить выбор из первой вкладки. Во второй попытаться отправить его снова или отменить: должно появиться сообщение о сохранении в другой вкладке. Исходный выбор остаётся на устройстве; второго запроса нет.
3. Разрешить успешный ответ. Дождаться локального подтверждения: выбор исчезает в обеих вкладках, более позднее чтение остаётся в очереди.
4. Повторить с сетевой ошибкой: после завершения запроса выбор остаётся, отмена или повтор во второй вкладке доступны. Отмена не откатывает изменение, которое сервер мог уже принять.
5. Во время задержанного запроса проверить независимый выбор другой книги. Повторить для другого аккаунта в отдельном локальном хранилище.

Это координация вкладок одного origin с новой версией приложения. Межустройственные конфликты по-прежнему обрабатываются серверной ревизией; полная автоматическая синхронизация не реализована.

## Серверный протокол закладок

На отдельной тестовой PostgreSQL примените все `services/api/db/migrations/*.up.sql` по порядку, затем выполните:

```sh
cd services/api
TEST_DATABASE_URL='postgres://lumyboo:test@127.0.0.1:55433/lumyboo?sslmode=disable' go test -race ./...
```

База должна быть предназначена для тестов. `TestPostgresBookmarkChanges` создаёт временных пользователей и проверяет повторы операций, переиспользование UUID, параллельные изменения одной ревизии, конфликт со старым устройством, tombstones, явное восстановление, изоляцию аккаунтов, совместимость с импортом/прежними UUID закладок и откат неуспешной записи вместе с receipt. HTTP-тесты отдельно проверяют вход, Origin/CSRF, ожидаемого владельца, обязательные поля, валидацию текста и отсутствие кеширования приватных ответов. CI запускает интеграционные тесты и цикл миграций up/down/up.

## Устойчивые клиентские запросы изменения закладок

`bookmark-choices.test.ts` проверяет модуль явных изменений закладок: IndexedDB v5, сохранение запроса до отправки, неизменный UUID/payload/revision при повторе после потери ответа и переоткрытия базы, сохранение конфликтов, изоляцию аккаунтов, ожидаемого account ID/CSRF на клиентском запросе и отклонение неверных подтверждений. Два подключения к одной базе проверяют Web Locks до коммита локального подтверждения. Удаление и повторное создание во время запроса не очищают более позднюю outbox; сбой локального подтверждения откатывает очистку целиком. Миграция v4 → v5 сохраняет прежние данные и выборы позиций.

Профиль использует этот модуль для явного сохранения отдельных закладок. Автоматический обмен пока не подключён. `rememberBookmarkChoice` принимает явно выбранный locator и ожидаемую серверную ревизию из `/bookmarks/state`, включая tombstones. Для удаления одного старого ключа из outbox недостаточно: требуется полный проверенный locator. `sendBookmarkChoice` отправляет только сохранённый запрос и подтверждает только зафиксированные до него операции. Полученный receipt не применяется как свежий снимок сервера и не заменяет локальные закладки. После конфликта нужен новый просмотр состояния; отмена не откатывает уже принятый сервером запрос и не очищает outbox.

Запуск: `npm test` и `npm run build` из корня. Серверный протокол отдельно проверяется Go/PostgreSQL-тестами выше. Живая межустройственная и браузерная приёмка клиентского модуля остаётся для подключения интерфейса.


## Явное сохранение закладок из профиля

`bookmark-review.test.ts` проверяет сопоставление по книге/изданию/абзацу, использование ревизии удалённого варианта для восстановления, отсутствие автоматического удаления по пустому локальному списку и исключение служебных полей из запроса. `account-save-status.test.ts` учитывает неподтверждённые закладки и конфликты даже без операций в outbox.

1. Войти, открыть книгу в читалке аккаунта, поставить закладку и выйти из читалки. В профиле открыть «Сравнить и сохранить закладку». Проверить email, книгу, подпись, главу, абзац, смещение и фрагмент текста. До подтверждения POST `/bookmarks/apply` не отправляется.
2. Подтвердить. Закладка появляется в серверном списке, покрытая операция уходит из очереди; время и места чтения остаются. Локальная закладка сохраняется.
3. В тестовом окружении прервать ответ `/bookmarks/apply` после серверного коммита. Закрыть окно и перезагрузить профиль: статус и «Открыть незавершённое сохранение закладки» остаются. Повторить: UUID, payload и ожидаемая ревизия прежние, дубликат не создаётся. Сбой локального подтверждения также оставляет повтор доступным.
4. Изменить ту же закладку с другого устройства после сравнения. Подтверждение возвращает конфликт; после reload кнопка повтора заблокирована. Отменить дальнейшие повторы: варианты загружаются заново, локальная закладка/очередь сохраняются.
5. Выбрать «Сравнить и удалить из аккаунта», проверить показанный фрагмент и подтвердить. Серверный список обновляется, локальная закладка остаётся. «Сравнить и восстановить в аккаунте» должно использовать ревизию tombstone и требовать нового подтверждения.
6. При ошибке загрузки вариантов новые изменения недоступны, но уже сохранённый неподтверждённый запрос можно открыть и повторить. Выход предупреждает о нём даже при пустой outbox. Смена аккаунта не показывает и не отправляет чужой запрос. Гостевые закладки копируются только отдельным явным действием.
7. Открыть профиль в двух вкладках. Во время задержанного POST в первой повтор/отмена во второй должны вернуть сообщение о другой вкладке. Более поздняя локальная правка остаётся в очереди после ответа на прежний запрос.


## Подготовка читалки при незавершённом изменении закладки

`npm run test -w apps/web -- src/lib/account-reading.test.ts` проверяет сохранение локальной подписи/смещения и отсутствующей закладки при незавершённом запросе без outbox. Сценарии включают перезапуск IndexedDB, конфликт, полные серверные снимки с закладкой и без неё, потерю ответа и выбор через другое подключение к базе. После отмены или подтверждения запроса следующий свежий снимок снова применяется; другие закладки и аккаунты не блокируются.

Для ручной проверки нужны тестовый аккаунт и управляемый API: загрузить закладку аккаунта в читалке, выйти, в профиле отправить удаление и оборвать ответ. Пока сохранение не подтверждено, снова открыть книгу и убедиться, что локальная закладка остаётся прежней независимо от наличия закладки в серверном снимке. Повторить после reload и с профилем в другой вкладке. Затем подтвердить повтор или отменить дальнейшие повторы, заново открыть книгу: применяется актуальный серверный список. Отдельно проверить, что остальные закладки продолжают загружаться. Не использовать production-данные для имитации потери ответа.


## Загрузка экранов по требованию

Профиль, знакомство, настройки и совместное чтение загружаются общим модулем `Personal`; вход, загрузки и читалка — отдельными динамическими модулями. Главная и каталог входят в начальную загрузку. `npm run build` показывает размеры модулей; `scripts/check-pwa.mjs` проверяет включение всех JS/CSS в precache, чтобы разделение кода не лишило установившую оболочку доступа к экранам без сети. Это уменьшает начальный JS, но не общий объём precache и не заменяет измерение скорости на устройстве.

1. Выполнить `npm run build`, затем `npm run preview -w apps/web -- --port 4194`. Открыть новый origin `http://127.0.0.1:4194/`, дождаться сообщения «Приложение сохранено на устройстве» в настройках.
2. В DevTools Network различать загрузку модулей страниц и фоновый precache service worker: профиль не должен входить в статическую цепочку импортов начального JS. Перейти в профиль, вход, загрузки и читалку. Экраны открываются в прежней рамке; при загрузке доступен текст ожидания, ошибка модуля попадает в экран восстановления маршрута.
3. Остановить preview-сервер. Открыть настройки, затем перезагрузить страницу. Экран должен восстановиться из оболочки. Повторить для `/downloads` и `/login`; вход без API не должен объявляться доступным. Для читалки предварительно скачать книгу — кеш модулей сам по себе не содержит её текст.
4. Проверить переходы и прямой перезапуск на Android/iPhone и в установленной PWA. Браузерный тест с остановленным сервером не заменяет эту приёмку.


## Явный приём закладки аккаунта на устройство

`npm run test -w apps/web -- src/lib/bookmark-download.test.ts` проверяет получение без исходящего эха, принятие tombstone, точную границу локальных операций, позднее создание/удаление/правку и одинаковое пересоздание из второго подключения IndexedDB, незавершённый выбор, истёкший/сменившийся вход, неверное издание/locator, атомарный откат при ошибке записи и Web Locks читалки/отправки.

1. Войти в тестовый аккаунт с серверной закладкой. В профиле выбрать «Сравнить и принять на устройство»: окно показывает email, книгу и оба варианта. Закрытие окна не меняет данные. Подтверждение добавляет/заменяет закладку устройства, серверный вариант остаётся прежним. Получение не вызывает POST `/bookmarks/apply` и не создаёт исходящую операцию.
2. Сделать локальную правку или удалить эту закладку, сравнить и принять вариант аккаунта. С ожидания отправки снимаются только показанные операции этой закладки; места чтения, время и другие закладки остаются. Перезагрузить профиль и проверить сохранность принятого варианта.
3. Удалить серверную закладку через явное действие аккаунта: локальная закладка остаётся. Отдельно выбрать «Сравнить и принять удаление на устройстве» и подтвердить. Локальная закладка исчезает, после reload не возвращается; серверный tombstone не меняется.
4. Между сравнением и подтверждением изменить эту закладку во второй вкладке. Подтверждение должно отказаться и предложить новое сравнение; новая правка и очередь остаются. Повторить с удалением и пересозданием одинакового варианта.
5. При открытой читалке той же книги приём запрещён до сохранения и выхода из неё. Незавершённая отправка этой закладки также блокирует приём. Другие книги/аккаунты не разделяют блокировку. Истёкший вход, смена аккаунта, ошибка проверки сессии и недоступное издание сохраняют локальные данные.

Это явный приём выбранного снимка, а не фоновый обмен или подтверждение актуальности всех данных. Для приёма нужна сеть, чтобы проверить сессию. Проверка с тестовым API не заменяет приёмку реальной API/БД и двух физических устройств.

Принимается явно выбранный снимок, который мог измениться на сервере после сравнения. Это не автоматическая синхронизация и не офлайн-вход. Тестовый API не заменяет проверку реальной API/БД и двух устройств.

## Серверные накопительные отчёты времени чтения

На отдельной тестовой PostgreSQL применить все миграции по порядку, включая `006_reading_sessions.up.sql`, затем выполнить:

```sh
cd services/api
TEST_DATABASE_URL='postgres://lumyboo:test@127.0.0.1:55434/lumyboo?sslmode=disable' go test -race ./...
```

База должна быть предназначена только для тестов. Интеграционный тест `TestPostgresReadingSessions` создаёт временных пользователей и роль с ограниченной записью для проверки атомарного отката при отказе вставки receipt. Для него требуется право создавать тестовые роли (в CI используется отдельная PostgreSQL).

Протокол: `POST /api/v1/reading-sessions/apply` принимает `accountId`, `operationId` и `session` (`sessionId`, `deviceId`, `bookId`, `version`, `day`, `milliseconds`). Требуются cookie входа, Origin приложения и `X-CSRF-Token`. `milliseconds` — накопленный целочисленный итог одной сессии от 1 до 86 400 000, а не добавка. Верхняя граница — технический предел одной записи, не проверка суммарного времени дня или достоверности чтения.

Тесты проверяют:

- Точный повтор UUID/payload возвращает исходное подтверждение, в том числе после более нового отчёта; новый UUID со старым/равным итогом не уменьшает время, не складывает снимки и не повышает ревизию.
- Параллельные снимки сходятся к наибольшему накопленному итогу; два одновременных повтора дают одну запись/receipt. Разные сессии/устройства не объединяются по книге и дню.
- У сессии неизменны устройство, книга, издание и заявленный день. Смена этих полей возвращает конфликт. Неверные календарные даты, нулевые/отрицательные/дробные/слишком большие итоги и неизвестные поля отклоняются.
- Владельцы изолированы, один session/operation UUID может независимо существовать у разных владельцев. UUID операции делит пространство с закладками и позициями: смена вида операции возвращает конфликт. Чужая/отсутствующая запись на GET даёт 404.
- Ошибка FK или записи receipt откатывает изменение целиком; повтор после устранения ошибки безопасен. Удалённый аккаунт не может отправлять отчёты.
- HTTP-проверки входа, Origin/cross-site, CSRF, ожидаемого аккаунта, текущего издания, no-store и безопасных ошибок выполняются до доступа к хранилищу.

`GET /api/v1/reading-sessions/{sessionId}` получает актуальный снимок только своего аккаунта. Receipt из POST может быть старее него: его нельзя применять как новый серверный снимок или подтверждение более поздних локальных изменений.

День здесь заявлен клиентом без подтверждённого часового пояса. Эти отчёты не начисляют XP, дневной план, серию, завершение книги или результат гонки. Веб-таймер и outbox пока не отправляют их; для следующего клиентского среза нужны зафиксированные устройство и версия книги. Старым локальным сессиям без этих метаданных нельзя приписывать их автоматически.
