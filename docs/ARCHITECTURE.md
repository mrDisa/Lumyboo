# Архитектура первого среза

- `apps/web`: React, TypeScript, Vite; TanStack Router с прямыми ссылками, TanStack Query для загрузки текста. Читалка загружается отдельным chunk. CSS-токены и графика извлечены из утверждённого прототипа; новые правила вынесены отдельно, стили читалки — CSS Module.
- `services/api`: модульный монолит Go/chi. `/healthz` — живой процесс, `/readyz` — доступность PostgreSQL. `/api/v1/catalog` — локальные фикстуры с поиском и пагинацией. Вход по email-коду и серверные сессии реализованы: текущий аккаунт доступен только по HttpOnly-cookie, изменяющие запросы защищены Origin и сессионным CSRF-токеном. Коды и токены хранятся хешированными; попытки, доставка и отзыв сессий проверяются на PostgreSQL.
- `contracts/openapi.yaml`: источник типов для `api.generated.ts`. Тип Book и заготовка клиента используют сгенерированный контракт.
- Веб пока читает **локальный manifest каталога**, а не API. Это позволяет проверять офлайн-сценарий до реализации серверного редакционного каталога. API seed соответствует manifest; `scripts/check-content.mjs` проверяет совпадение.
- Dexie v3 (миграции из v1/v2 без удаления данных): настройки, полка, позиции, закладки, загрузки, локальные сессии. Данные одного гостевого браузера; вход в серверный аккаунт пока не переносит их и не меняет владельца. Не использовать этот namespace для аккаунтов без LUM-028/033.
- Cache Storage `lumyboo-books-v1`: только явно скачанные общедоступные технические тексты. SHA-256 и версия проверяются перед записью и чтением. После очистки браузером отметка загрузки снимается при запуске или открытии текста.
- Workbox precache: оболочка, локальные шрифты и изображения. Тексты книг не включены в precache. `/api/` не кешируется; нет общего runtime-кеша авторизации и приватных ресурсов.
- Позиция: версия, номер главы, ID абзаца, доля прокрученной высоты абзаца. Перестройка текста не превращает экранную страницу в ID. Прежний locator при смене издания архивируется. Автоматическое сопоставление абзацев разных изданий и конфликты между устройствами ещё не реализованы.
- Локальные сессии: monotonic clock, запись накопленного значения под одним UUID. Повторный snapshot заменяет предыдущий, а не добавляет секунды. Временные разрывы >5 с не начисляются; пограничные случаи при подвисании/блокировке требуют устройства. Нет XP, статуса «прочитано» и серверного доверия к этим данным. Покрытие показанного текста хранится отдельно от времени и позиции, как описано ниже.
- Worker — явно не реализован; команда завершается с объяснением. River/sqlc/S3-клиент добавляются вместе с первыми реальными потребителями, не имитируются пустым процессом. PostgreSQL/MinIO подготовлены в compose.

## Техническая проверка EPUB (LUM-017/018, частично)

Для первого сценария выбрана нормализация доверенных редакционных EPUB в текстовый JSON: браузер отображает строки средствами React и никогда не вставляет HTML книги. Импортёр использует стандартную библиотеку Python, проверяет archive traversal, дубли, размер, symlink, шифрование, DTD/entities и внешние spine-ресурсы. Скрипты и неподдерживаемый мультимедийный контент отклоняются.

Поддержаны линейные XHTML-главы, кириллица, заголовок главы, абзацы и текст простого inline-форматирования. В этом срезе inline-начертание нормализуется в обычный текст. Изображения, таблицы, SVG, математическая разметка и интерактивные сноски **не поддержаны**. Универсальная поддержка EPUB не заявляется. Требуется дальнейшая проверка на 5–10 книгах; движок/нормализатор ещё не признан окончательно подходящим для всего каталога.

Исходник тестовой книги: `content/fixtures/room-for-stories.epub`. Его импорт даёт байт-в-байт тот же JSON, который открывает приложение. Импортёр не публикует книгу и всегда выдаёт `rights_status: pending`: редакторская запись не является автоматической проверкой прав.

## Защита офлайна и обновления

Worker самодостаточен: Workbox runtime встроен, внешних importScripts нет. Первая установка использует clientsClaim; skipWaiting остаётся выключенным до явного применения обновления. Публичные ресурсы с постоянными именами имеют content revision; дубли precache устранены. Регистрация выполняется singleton-модулем, а не побочным эффектом React initializer.

Обновление, активированное другой вкладкой, не вызывает автоматическую перезагрузку читалки. Перезагрузка выполняется по запросу пользователя вне читалки. Настройки показывают проверенное наличие оболочки и активного controller.

Загрузка текста читает поток с контролем размера, показывает процент, затем проверяет SHA-256 и обязательные chapter/paragraph IDs. Неудачный повтор не удаляет ранее проверенную копию. Сверка загрузок удаляет ложные отметки после очистки или повреждения кеша. Раздел `/downloads` доступен без сети и позволяет удалить текст, оставив личные данные чтения.

При смене издания прежняя позиция архивируется транзакционно в `positionHistory` до записи новой. Закладки предыдущих версий сохраняются в базе, но не используются как locator нового издания.

## Локальная очередь изменений

Изменения полки, настроек, позиций, закладок (включая удаление) и snapshots времени записываются вместе с outbox одной транзакцией IndexedDB. Ошибка очереди откатывает изменение. Операция содержит UUID, версию формата, постоянный случайный ID установки, монотонную последовательность и явную область `guest`. ID установки не является ID пользователя и не даёт прав на сервере.

Очередь хранит последний ещё не отправленный snapshot каждой сущности; удаление остаётся отдельным tombstone. Операции в состоянии `sending` не изменяются: будущий отправитель должен пометить выбранный пакет этим состоянием транзакционно до сетевого запроса и повторять его с прежними ID до подтверждения. Последовательность задаёт локальный порядок, а не серверную версию и не приоритет при конфликте. Время сессии передаётся накопленным значением, а не прибавлением секунд.

Отправителя и серверного приёма пока нет. Вход не привязывает гостевую очередь к аккаунту. Старые данные при миграции остаются локальными и не превращаются автоматически в операции: их включение в перенос требует отдельного подтверждённого сценария LUM-033. Кеши загрузок и история старых изданий в очередь не входят. Данные читаются непосредственно из локальных таблиц, поэтому накопление очереди не блокирует офлайн-чтение; ошибка её записи обрабатывается как ошибка сохранения.

## Явное копирование гостевой полки (LUM-033, первый срез)

`GET /api/v1/shelf/` читает полку только текущей серверной сессии. `POST /api/v1/shelf/import` принимает явный список книг и ожидаемый account ID: владелец определяется по cookie, а несовпадение ожидаемого ID отклоняется. Запрос защищён Origin/CSRF; ответы `no-store`. Доступные ID проверяются по текущему локальному каталогу пилота, не по произвольным данным клиента.

Копирование выполняется одной PostgreSQL-транзакцией. Блокировка пользователя сериализует его импорты; `ON CONFLICT DO NOTHING` сохраняет имеющиеся книги и делает повтор после утраты ответа безопасным. Схема `shelf` уже существует, новая миграция не требуется. Это идемпотентность добавления книг, а не общий протокол обработки outbox/серверных ревизий по LUM-035.

В профиле серверная полка показана отдельно от гостевой. Копирование требует подтверждения списка и email; не удаляет и не меняет локальные данные. Кеш запроса разделён по аккаунту, уничтожается после отключения подписчика, а ответ другого аккаунта отклоняется. При проверке/ошибке сессии блок аккаунта скрыт. Прогресс и закладки остаются гостевыми; гостевая очередь не отправляется и не привязывается к cookie. Полный account namespace, перенос закладок/позиций, конфликты и автоматическая синхронизация остаются следующими задачами.

## Копирование гостевых закладок (LUM-033, второй срез)

`GET /api/v1/bookmarks/` читает активные закладки текущего аккаунта; `POST /api/v1/bookmarks/import` принимает подтверждённый список до 100 locators и ожидаемый account ID. Cookie определяет владельца; Origin/CSRF/account assertion защищают перенос. Каждая запись проверяется по версии книги, номеру главы, реальному paragraph ID, смещению [0,1) и длине подписи. Индекс paragraph IDs сверяется с книгами в `check-content.mjs`.

Миграция 003 добавляет **неопубликованные** метаданные текущих пилотных изданий для внешних ключей закладок: техническая история — development_fixture, фрагменты — pending. Прав на публикацию не добавляет; существующие строки не изменяет. Откат не каскадирует личные данные и откажет, пока есть ссылки на эти издания.

Импорт сериализуется блокировкой пользователя и выполняется одной транзакцией. Стабильный серверный UUID зависит от владельца, книги, версии и абзаца. Дополнительная проверка естественного ключа учитывает прежние UUID. Существующие подписи, смещения и tombstones имеют приоритет: повтор не дублирует запись, не перезаписывает её и не восстанавливает удаление. Ошибка одного элемента откатывает весь пакет. Часы устройства не задают приоритет.

Профиль показывает отдельный список аккаунта и диалог выбора/подтверждения email. Ответы другого аккаунта отклоняются; HTTP/Query кеш не общий. Гостевые данные и outbox не меняются. Позиции чтения, account namespace, загрузка закладок в читалку и автоматический обмен остаются открытыми задачами; этот срез не объявляется полной синхронизацией.

## Явный перенос позиции и конфликты (LUM-033/035/037, срез)

`GET /api/v1/positions/` возвращает текущие locators аккаунта с серверной ревизией. `POST /api/v1/positions/choose` принимает UUID операции, ожидаемую ревизию (0 для отсутствующей записи), locator и ожидаемый account ID. Владелец определяется сессией; Origin/CSRF/account assertion обязательны. Проверяются обязательные поля, текущая версия/глава/реальный paragraph ID, смещение и безопасный для JavaScript диапазон ревизии. Часы устройства и процент прогресса не определяют приоритет.

Транзакция блокирует пользователя, проверяет receipt операции и затем ожидаемую ревизию. Совпавший UUID с другим payload отклоняется. Прежнее место архивируется в `reading_position_history` (миграция 004); позиция, новая ревизия и receipt `processed_operations` фиксируются вместе. Повтор исходной операции возвращает её первоначальный результат, даже если текущая позиция уже изменилась. Конкурирующие запросы одной ревизии не могут оба примениться. Будущие писатели позиции должны придерживаться той же блокировки/проверки ревизий.

Профиль показывает два места, а диалог дополнительно загружает проверенный текст книги для сравнения глав/абзацев/фрагмента. Выбор устройства заменяет серверный locator после подтверждения. Выбор «Оставить место аккаунта» закрывает сравнение без записи. Гостевая позиция и outbox не меняются: аккаунт не копируется в общий гостевой namespace. При 409 сохранение из старого диалога блокируется, данные перечитываются, нужно повторное сравнение. При сетевой неопределённости повтор в открытом диалоге сохраняет прежние UUID/payload. После подтверждения перечитывается актуальное состояние вместо установки потенциально устаревшего receipt в кеш.

Это ручное сохранение позиции, а не завершённая синхронизация: account namespace читалки, автоматическая очередь/повторы после перезапуска и получение истории через UI ещё впереди. До этого читалка продолжает с гостевого места устройства; сохранение locator не означает полное прочтение и не начисляет наград.

## Читалка аккаунта и отдельное локальное хранение (LUM-028/033)

Ссылки серверной полки и мест аккаунта открывают `/account/read/$bookId`. `/read/$bookId` сохраняет гостевой режим. Читалка аккаунта требует успешно проверенной сессии, ответа серверных мест/закладок именно этого пользователя и дополнительной проверки перед подготовкой локального состояния. Проверка/ошибка сессии скрывает приватную читалку; auth-события соседних вкладок продолжают работать через общий `useAccount`. По умолчанию аккаунт не открывается офлайн заново: сохранённые данные не являются подтверждением сессии.

Каждый аккаунт использует отдельную Dexie-базу `lumyboo-account-<uuid>` с той же v3-схемой. Места, закладки, история, локальные секунды и outbox отделены от гостя и других аккаунтов. Database instance передаётся в читалку явно; поздние записи при размонтировании остаются в захваченном namespace. У операций явный scope `account:<uuid>`; старый гостевой namespace/очередь не меняются. Книги пилота общедоступны технически, их проверенный кеш остаётся общим; приватных файлов в нём нет. Параметры оформления остаются настройками устройства; читалка аккаунта не меняет гостевой currentBook.

Первое открытие получает серверный locator и закладки без постановки скачанного состояния обратно в outbox. Если локальное место отличается, пользователь явно выбирает вариант; выбор серверного архивирует прежнее локальное место и удаляет только заменённую pending-операцию позиции. Перед записью локальный snapshot проверяется повторно в транзакции, чтобы не затереть изменение другой вкладки. Обновление закладок учитывает локальные pending/sending изменения и незавершённые `bookmarkChoices` (включая конфликты и выборы без outbox). Проверка выполняется в той же IndexedDB-транзакции: до подтверждения или отмены повтора снимок не меняет наличие, подпись и locator соответствующей локальной закладки, в том числе при выборе из другой вкладки. Локальные удаления не восстанавливаются; нетронутые закладки, отсутствующие в полном серверном ответе, удаляются. Пакет подготовки атомарный.

Профиль сравнивает приватное место аккаунта на устройстве с сервером, а при его отсутствии предлагает гостевое. Ручное сохранение на сервер сохраняет прежний протокол ревизий. При выходе наличие outbox требует явного выбора: остаться или выйти, оставив изменения в локальном хранилище того же аккаунта. Ожидаемый ID дополнительно проверяется перед logout/logout-all. Локальные базы не стираются при выходе: до повторного подтверждённого входа они не показываются через UI. Это разделение доступа интерфейса, а не шифрование данных от владельца браузера/доступа к диску.

Защита обновления PWA и компактная рамка распространяются на оба маршрута чтения. Автоматическая отправка outbox, синхронизация локальных правок закладок/времени и полноценное офлайн-восстановление аккаунта остаются следующими задачами; локальный счётчик профиля помечен гостевым.

## Протокол изменений закладок аккаунта

`GET /api/v1/bookmarks/state` возвращает полный снимок закладок текущего аккаунта, включая `revision` и `deleted`. Старый `GET /bookmarks/` по-прежнему отдаёт только активные закладки для существующей читалки. Миграция 005 добавляет серверную ревизию: у прежних закладок и tombstones она равна 1.

`POST /api/v1/bookmarks/apply` принимает одну операцию: `accountId`, UUID `operationId`, `expectedRevision`, полный `bookmark` и обязательный `deleted`. Ревизия 0 означает отсутствие записи. Создание, изменение и удаление увеличивают ревизию; удаление отсутствующей записи создаёт tombstone. Восстановить её можно только явной новой операцией с актуальной ревизией. Проверяются сессия, Origin, CSRF, ожидаемый аккаунт, обязательные поля и текущая версия/глава/абзац пилотной книги. Часы клиента не влияют на приоритет. Старые издания пока не принимаются, как и при импорте.

Изменение и receipt фиксируются одной транзакцией под блокировкой пользователя, общей с гостевым импортом. Два изменения одной ревизии не применяются одновременно. UUID операции принадлежит аккаунту и разделяет пространство с операциями позиций: другое содержимое или тип операции дают `operation_reused`. Точный повтор возвращает первоначальный результат даже после последующих изменений; это подтверждение операции, а не свежий снимок. После подтверждения клиент должен заново получить состояние. Конфликт ревизий возвращает `bookmark_conflict`, не записывает receipt и требует нового сравнения. Гостевой импорт сохраняет приоритет существующих закладок и удалений.

Это серверная часть LUM-035. Клиентская outbox ещё не отправляет изменения закладок через этот протокол; автоматическая синхронизация в интерфейсе не заявляется. Перед её подключением нужны устойчивое хранение отправляемого payload/ревизии, точные границы подтверждения, повтор после перезапуска и обработка конфликтов без потери более поздних локальных правок.

## Локальные наблюдения текста

Dexie v6 добавляет таблицу `coverage`: ключ книги/версии/устойчивого ID абзаца, ID главы и объединение непересекающихся диапазонов долей абзаца. Интервал геометрически обрезается границами экрана, viewport и липкой шапкой. Наблюдение выполняется раз в секунду только при активном видимом тексте, готовом восстановлении и положительном интервале ReadingClock; диалог/потеря фокуса/скрытие/длительная приостановка не создают наблюдений. Cleanup и явный flush не снимают DOM: после смены главы React уже мог отрисовать новый текст.

Транзакция объединяет пересечения и сохраняет пропуски, повторные снимки не расширяют диапазон. Неизменившееся значение не переписывается. Гость и аккаунты используют отдельные базы; другие книги/издания — отдельные ключи. Миграция создаёт пустую таблицу, не выводит покрытие из времени или позиции. Гостевые наблюдения остаются локальными; наблюдения аккаунта имеют отдельную outbox и явную отправку из профиля. Приём места/закладки и история времени их не заменяют.

Это приблизительные доли геометрии абзаца при текущей вёрстке, без точного сопоставления символов при изменении шрифта. Сам показ не доказывает чтение; между тиками наблюдений нет. При ошибке записи фрагменты остаются в буфере открытой читалки и повторяются при следующих тиках/сохранении; закрытие процесса до успешного коммита может потерять этот буфер. Ни статус завершения, ни процент прочитанного, ни награды из этих данных пока не вычисляются.

Буфер покрытия создаётся для открытой читалки с фиксированными content/database и переживает смену главы/диалога. Все обращения к flush используют одну выполняющуюся запись; финальный flush дожидается и наблюдений, добавленных во время записи. Успех удаляет только совпадающий снимок буфера, ошибка оставляет данные для следующего вызова, включая фрагменты предыдущих глав. Ошибка финального flush не разрешает штатный выход/освобождение Web Lock. Данные ещё не записанного буфера не переживают принудительное закрытие вкладки/процесса.


## Повтор локальной записи времени

Открытая читалка держит отдельный `ReadingSessionRecorder`, привязанный к content/database. Он сохраняется при смене главы и открытии диалога; смена дня и разделение сессии по пределу 24 часа не удаляют неподтверждённые totals. Для каждого session UUID буфер хранит последний накопительный снимок, записи выполняются последовательно через существующую атомарную транзакцию sessions/outbox/metadata. Суммирование повторов не выполняется.

Подтверждение удаляет только записанный снимок; поздние секунды и новые сессии остаются до своего коммита. Параллельный финальный flush ждёт всю очередь; отказ записи отклоняет ожидающие вызовы, сохраняет остаток для следующего тика/явного выхода и не разрешает освободить защиту читалки. Буфер до коммита находится в памяти: принудительное закрытие процесса всё ещё может потерять незаписанное время. Серверная отправка использует прежнюю устойчивую outbox после локального коммита.


## Серверное хранение наблюдений текста

`reading_coverage` (миграция 008) хранит объединение геометрических диапазонов по user/book/version/paragraph. `POST /reading-coverage/apply` принимает один абзац доступного технического издания с operation UUID и expected account ID. HTTP проверяет session/Origin/cross-site/CSRF и принадлежность paragraph выбранному изданию. Сервер не выводит покрытие из места, времени или посещения последней главы.

Диапазоны на проводе — пары целых миллионных долей `[from, to]`, 0 ≤ from < to ≤ 1 000 000. На запрос допускается до 64 диапазонов и 8192 байт; после объединения — до 256 непересекающихся фрагментов абзаца. Пересечения/соседние границы сливаются, пропуски сохраняются. Превышение лимита возвращает `coverage_fragment_limit` без изменения/receipt; клиент не должен заполнять невиденные промежутки или удалять наблюдения ради обхода лимита.

Блокировка user и общий namespace `processed_operations` сериализуют запросы вместе с позициями/закладками/временем. Coverage и receipt фиксируются одной транзакцией. UUID привязан к payload/kind; точный повтор возвращает исходное подтверждение, которое может быть старее текущего покрытия. `GET /reading-coverage/{bookId}?version=...` выдаёт приватные живые страницы по 1–50 абзацев, default 20, keyset по ID абзаца с C collation. Это порядок ID, не порядок чтения; обновление диапазонов не двигает строки, новые ранние ID появляются при обновлении с начала. Чтение прежних изданий разрешено в пределах владельца.

Браузер явно отправляет локальные наблюдения аккаунта и получает диапазоны выбранного проверенного издания с добавляющим объединением. Из этих приблизительных геометрических данных не вычисляются завершение, минуты, XP, серия или результат гонки.


## Клиентская очередь покрытия

Запись аккаунтного coverage атомарна с `coverage.put` в общей outbox и metadata. Гость не создаёт этих операций. Флаг `queued` в записи coverage означает, что снимок уже был поставлен в очередь; это не подтверждение сервера. Прежние v6-записи с известным book/version/paragraph ставятся в очередь один раз перед автоматическим или ручным сохранением, либо при повторном наблюдении этого абзаца. Флаг и операции записываются одной транзакцией; схема IndexedDB остаётся v6.

Снимок абзаца преобразуется в целые миллионные с округлением внутрь и устранением двоичного шума для уже квантованных границ. Непредставимые фрагменты короче миллионной не отправляются; локальная геометрия остаётся. Снимок разбивается на части до 64 диапазонов с ключом JSON [book,version,paragraph,chunk]. Новая запись удаляет только pending-части того же абзаца и добавляет новый полный снимок. Sending-части неизменны, даже если последующее наблюдение сократило число частей. Сервер объединяет повторы; отправитель не обходит серверный лимит 256 фрагментов заполнением невиденных промежутков.

`sendReadingCoverage` берёт отдельный общий Web Lock аккаунта до последнего локального acknowledgement, проверяет живую сессию и отправляет до 50 операций, uncertain сначала. POST повторяет сохранённые UUID и целочисленный payload. Проверяется владелец, точное издание/paragraph и канонический ответ, покрывающий отправленные диапазоны. Подтверждение удаляет только совпадающую sending-операцию; поздние наблюдения, локальный coverage и другие типы outbox не заменяются receipt. При потере ответа/ошибке ack операция остаётся для точного повтора. Ручная отправка отменяется при закрытии профиля. Автоматический отправитель живёт на уровне приложения и отменяется при смене/закрытии владельца; оба используют один Web Lock. Получение доступно явно из профиля и автоматически в открытой читалке.


## Получение покрытия выбранного издания

В профиле можно выбрать книгу текущего каталога и дополнить её локальные наблюдения сохранёнными в аккаунте. Перед получением загружается проверенный по манифесту текст: только его точные book/version/paragraph/chapter используются для валидации. `receiveReadingCoverage` берёт тот же account Web Lock, что отправитель, и проверяет живой вход до загрузки страниц и непосредственно перед локальным коммитом.

Все живые страницы по 50 абзацев сначала загружаются в память. Проверяются owner, издание, известные paragraph ID, канонические целые ranges, строгий порядок PostgreSQL C по UTF-8 и отсутствие дублей. Непустой cursor обязан совпадать с последним ID полной страницы и продвигаться вперёд. Число уникальных строк ограничено абзацами проверенного текста. Новые серверные строки до пройденного курсора могут появиться только при повторном получении с начала: это не единый межстраничный snapshot.

После полной проверки одна coverage-транзакция повторно читает текущие локальные ranges и объединяет их с серверными, сохраняя пропуски и наблюдения, появившиеся во время запроса. Ошибка сети/валидации/хранилища или отмена до коммита не оставляет частичного приёма. Пустая история ничего не удаляет. Получение не трогает позиции/закладки/секунды/outbox/metadata и не подтверждает pending/sending. Новые серверные строки имеют queued-marker без создания исходящих операций; прежний marker локальной строки сохраняется. У legacy-наблюдений без marker последующее сохранение по-прежнему может поставить полный объединённый снимок в очередь. Повтор не меняет уже совпадающие данные. Завершение книги/награды не вычисляются.


## Автоматическая отправка фрагментов

`AutomaticReadingCoverage` запускается только для подтверждённого аккаунта. Общий с временем планировщик `reading-auto` проверяет очередь при запуске, событии online и каждые 30 секунд; полный пакет 50 продолжает через 1 секунду. Живая сессия проверяется перед каждым пакетом и повторно внутри coverage-lock. Проверка работы включает прежние локальные наблюдения без queued-marker; гость, чужие и повреждённые операции не отправляются.

Сетевые ошибки/429/5xx повторяются через 5 секунд — 5 минут с учётом Retry-After; online не обходит задержку. Занятый lock отправки/получения повторяется через 5 секунд. Ошибки входа, валидации, receipt и хранилища приостанавливают отправителя; успешное ручное сохранение или новый запуск владельца возобновляет его. Cleanup отменяет запрос и будущие пакеты, сохраняя sending для точного повтора. Статус виден в профиле. Получение работает в открытой читалке и явно из профиля; фоновая работа закрытого приложения, завершение и награды не добавлены.


## Обновление покрытия открытой книги

Читалка аккаунта запускает конечное получение текущего издания при открытии, после успешного получения — при возвращении фокуса/видимости и восстановлении сети. Дополнительно раз в 60 секунд проверяются сеть, видимость и фокус; при выполнении условий завершённое получение обновляется с первой страницы, включая прежнюю пустую историю. Это позволяет получить новые наблюдения другого устройства без выхода из текста.

Интервал принадлежит получателю открытой книги и удаляется вместе с отменой запросов при cleanup. Тик не запускает параллельный запрос, не обходит backoff/Retry-After и не возобновляет окончательно остановленный получатель. Проверка видимости ограничивает периодические обновления; уже начатый запрос и повторы после временных ошибок используют прежний планировщик. Данные объединяются прежним атомарным загрузчиком без изменения outbox, позиции, закладок и времени. Этот обмен не подтверждает полное прочтение и не выдаёт наград.
